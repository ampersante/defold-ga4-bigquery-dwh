# Карта данных: 20 вопросов → события, таблицы, витрины

Дополняет [architecture.md](architecture.md) и [monetization-attribution.md](monetization-attribution.md). Здесь — **каталог событий** (§3). Его машинная версия — YAML-файл трекинг-плана в репозитории игры; этот документ описывает тот файл.

**Корень:** на любой из 20 вопросов можно ответить, только если выполнены два условия. Первое: у каждого события и каждого игрока есть одинаковые метки сравнимости — билд, версия конфига, эксперименты, канал, когорта (когорта — группа игроков с общими параметрами установки: датой, платформой, страной, билдом). Второе: у ключевых моментов игры есть снимок состояния игрока. Поэтому план состоит из трёх частей: служебные поля на всех событиях (§2), несколько событий-снимков (§3) и справочники версий (§4).

## 1. Где отвечаем на каждый вопрос

Обозначения:

- **DWH** — ответ считается в хранилище данных BigQuery.
- **AF** — AppsFlyer.
- **консоли** — кабинеты сетей и сторов.
- **позже** — вне текущего решения, но модель к нему готова.

Термины из таблицы:

- **витрина** — готовая таблица с посчитанными метриками, из неё строятся дашборды;
- **слой глубины** — группа игроков, продвинувшихся в игре одинаково (одинаковые `lvl` и `sn`);
- **стандартизация по составу** — пересчёт показателя так, чтобы у сравниваемых каналов состав аудитории считался одинаковым;
- **самоотбор** (selection bias) — механику чаще используют те, кто и так играет усерднее, поэтому связь «механика → удержание» может оказаться кажущейся;
- **A/B с контрольной группой** — часть игроков не получает фичу, результаты двух групп сравнивают;
- **дифф** — список отличий между двумя версиями.

## 2. Метки сравнимости — что есть у каждого события и игрока

### 2.1 На каждом событии (добавляет обёртка `analytics.lua`)

| Поле | Смысл |
|---|---|
| `eid` | ID события: по нему убираются дубли ([architecture.md §2.1](architecture.md)) |
| `seq` | Порядковый номер события на установке: по пропускам в нём видна доля потерянных событий. Пропуск виден, только если после потерянных событий пришло следующее, поэтому это нижняя граница потерь: потерянный хвост (последние события) игрока, который не вернулся, не виден (§3.1) |
| `cts` | Время события на устройстве игрока |
| `build` | Версия билда |
| `cfg` | Версия шаблона Remote Config, с которой играет клиент |
| `sn` | Номер сессии на установке (1 = первая сессия на этой установке). Первая сессия игрока — `sn = 1` на его первой установке (§2.2) |
| `lvl` | Ключевой прогресс (уровень или глава) |

Эти 7 полей занимают 7 из 25 мест под параметры события. На смысловые параметры остаётся 18. Лимит соблюдается механически: проверка YAML трекинг-плана при сборке и счётчик параметров в обёртке (правила — [architecture.md §2.1](architecture.md)); событие, у которого Firebase всё же отбросил параметры или обрезал значение, несёт `firebase_error` и видно в `dq`. Группы A/B Firebase ставит сам как user property (свойство игрока, не события) `firebase_exp_<id>`. Места в параметрах события они не занимают [факт].

### 2.2 На игроке (`dim_player`, вычисляется в DWH)

- **Когорта:** дата установки, платформа, страна, билд установки, `cfg` установки — по первой установке игрока.
- **Канал:** `ua_source`, `ua_campaign_id`, `ua_adset_id`, `ua_ad_id`, `ua_site_id`, `attribution_quality`. Храним **ID**, а не только имена: имена кампаний меняют, ID нет. По этим же ID будет считаться будущая таблица затрат (§6). Канал берётся из первой установки игрока (с самым ранним первым событием). Если у неё нет `ua_attribution`, канал — «неизвестно».
- **Аккаунт:** тип входа (`gamecenter` / `google` / `device`), дата привязки.
- **Эксперименты:** все группы A/B с датой попадания. Firebase назначает группу установке, а не игроку: вариант считается по ID эксперимента и ID установки Firebase [факт]. После переустановки или на втором устройстве игрок может попасть в другую группу. Группа игрока — его первое назначение. Игроки, у которых в одном эксперименте больше одной группы, учитываются отдельно и исключаются из `ab_results` и `ab_monetization`; их доля видна в `dq` (проверках качества данных). Серверная выручка игрока относится к его группе.
- **Тест:** `test_id` из реестра `ref_tests`, если установка попала в окно теста.

У одного игрока может быть несколько установок: переустановка, второе устройство. Каждая установка — строка в `dim_install` (одна строка на `user_pseudo_id`: `player_id`, время первого события, билд, поля `ua_attribution`). Поздняя установка из новой кампании — это повторное привлечение: она видна в `dim_install` и не перезаписывает когорту и канал в `dim_player`. Первая сессия игрока — `sn = 1` на его первой установке. По ней считаются вопросы 1, 6 и 7.

### 2.3 Реестр тестов `ref_tests` (ответ на вопрос 19)

Небольшая таблица в репозитории Dataform (инструмент, который собирает таблицы в BigQuery из кода). Задаётся YAML или CSV и превращается в таблицу. Заполняется руками при запуске каждого теста:

| Поле | Пример |
|---|---|
| `test_id`, `name` | `sl_ph_2026_11`, «Софт-ланч Филиппины, ноябрь» |
| `start`, `end` | даты окна установок |
| `geos`, `platforms`, `sources` | `PH`; `android`; `applovin, mintegral` |
| `builds`, `experiments` | диапазон билдов; ID A/B-тестов |
| `variants` | значения параметров Remote Config в каждом варианте эксперимента: `0` (контроль) — `pack_price = 4.99`, `1` — `pack_price = 2.99`; записываются при запуске теста (§4) |
| `tracking_plan_version` | версия YAML трекинг-плана |
| `notes`, `comparable_with` | что меняли; с какими тестами корректно сравнивать |

Витрины считаются по меткам когорты, поэтому любой тест можно сравнить с любым другим. Дашборд показывает рядом с цифрами `tracking_plan_version` и зрелость когорты (сколько времени прошло с установки). Если у сравниваемых тестов разные версии трекинг-плана или разные определения метрик (§5), сравнение помечено как несопоставимое, а не молча смешано.

## 3. Каталог событий

Имена событий короткие. Событий мало, параметров много. Новое имя заводится, только если параметры существующего события не закрывают вопрос.

### 3.1 Сессия и техника (вопросы 6, 18)

| Событие | Когда | Параметры |
|---|---|---|
| `session_begin` | старт или возврат из фона | `start` (cold/warm), `net` (wifi/cell/none), `load_ms`, `bg_s` (сколько был в фоне), `prev_end` (только холодный старт: `bg` / `crash` / `killed_fg` — как закончилась прошлая сессия, ниже) |
| `load_step` | только холодный старт, по шагам загрузки | `step` (boot / firebase / auth / config / assets / first_frame), `ms`, `ok`, `err` |
| `session_snapshot` | уход в фон (событие окна Defold `FOCUS_LOST` / `ICONIFIED`) | `dur_s`, `last_action`, `last_screen`, `soft`, `hard`, `energy`, `goal_id`, `goal_pct`, `last_result`, `rewards_pending`, `notif_next` (тип ближайшего локального пуша), `rcv` (1 — только у восстановленной копии, ниже) |
| `app_crash` | на следующем холодном старте сразу после инициализации Firebase, если Defold `crash.load_previous()` вернул дамп (данные о сбое) | `signal`, `crash_build`, `crash_ts` |
| `app_error` | нефатальная ошибка | `code`, `where` |
| `auth` | вход в Nakama | `method` (gamecenter/google/device), `ok`, `is_new`, `err` |
| `account_link` | привязка Game Center / Google к анонимному аккаунту | `method`, `ok`, `conflict` (аккаунт уже был у другого профиля) |

Бюджет параметров: у `session_begin` 5 смысловых, у `session_snapshot` 12 — оба в пределах 18 (§2.1).

**Доставка `session_snapshot`.** События, записанные при уходе в фон, Firebase хранит на устройстве и отправляет при следующем запуске [факт для SDK]; iOS SDK хранит их в SQLite на устройстве [факт: Firebase iOS reference]. В какой момент после вызова `logEvent` событие записано на устройство, не документировано ни для iOS, ни для Android [не найдено]; расширение Defold вызывает нативный `logEvent` синхронно из Lua [факт по коду расширения]. Схема от этого момента не зависит:

- При уходе в фон обёртка в том же вызове, где логирует `session_snapshot`, пишет это событие целиком (все параметры, включая `eid`, `seq`, `cts`) в сохранение игры. В сохранении лежит только последний снимок: следующий уход в фон его перезаписывает.
- На следующем холодном старте, после инициализации Firebase, игра логирует сохранённый снимок ещё раз с теми же `eid`, `seq`, `cts` и `rcv = 1`, затем стирает его из сохранения.
- Дедупликация по `eid` оставляет одну строку ([architecture.md §1](architecture.md)). Если дошла только копия, строка помечена как восстановленная.

Итог: у каждого вернувшегося игрока последний `session_snapshot` доходит, что бы ни случилось с оригиналом, а доля строк, известных только по копии, — точная доля потерь оригинала при уходе в фон. Оценкой остаётся только хвост игроков, которые не вернулись: их сохранённая копия не отправится никогда. Доля потерь у них берётся из доли восстановленных строк у вернувшихся.

**Как закончилась прошлая сессия (`prev_end`).** На холодном старте `session_begin` несёт `prev_end`:

- `crash` — `crash.load_previous()` вернул дамп;
- `killed_fg` — дампа нет, но прошлая сессия так и не ушла в фон: система убила игру на переднем плане;
- `bg` — прошлая сессия закончилась уходом в фон.

Механизм: флаг «на переднем плане» в сохранении ставится на `session_begin` и снимается, когда записан `session_snapshot`. На холодном старте: есть дамп → `crash`; флаг стоит, дампа нет → `killed_fg`; иначе → `bg`. Игрок смахивает игру из списка приложений уже после ухода в фон, поэтому это `bg`.

**Краши.** `app_crash` пишется на холодном старте сразу после инициализации Firebase из `crash.load_previous()`. Дамп читается один раз: после чтения он удаляется. Модуль crash Defold на iOS и Android ловит сигналы SIGSEGV, SIGBUS, SIGTRAP, SIGILL, SIGABRT; файл дампа каждый раз перезаписывается, поэтому хранится только последний краш [факт по коду движка Defold, engine/crash]. Не ловятся: убийство процесса системой (SIGKILL — нехватка памяти, watchdog, ANR), потому что SIGKILL перехватить нельзя [вывод], — такие случаи видны как `prev_end = killed_fg`; ошибка Lua — это не краш, движок продолжает работу [вывод]; необработанное исключение Java на Android — не сигнал [вывод]. Краши до инициализации Firebase и исключения Java в DWH не видны; они видны только суммарно: в Android Vitals и Xcode Organizer. Поэтому Firebase инициализируется первым.

### 3.3 Прогресс и баланс (вопросы 7, 10)

| Событие | Параметры |
|---|---|
| `level_start` | `level_id`, `mode`, `attempt`, `power` (сила игрока по формуле игры), `difficulty` (из конфига), `boosters_pre` |
| `level_end` | `level_id`, `attempt`, `result` (win/lose/quit), `dur_s`, `score` или `stars`, `progress_pct`, `fail_reason`, `power`, `difficulty`, `boosters_used`, `continue_used`, `soft`, `hard` |
| `item_upgrade` | `item_id`, `from_lvl`, `to_lvl`, `cost`, `currency`, `power_after`, `after_loss` (1, если прошлый уровень проигран) |

Поля `power` и `difficulty` показывают механизм — почему игроки отваливаются, а не только где (правило «где ≠ почему»). Формулу `power` геймдизайн фиксирует до первого билда. Без неё вопрос 10 закрывается только наполовину.

### 3.4 Экономика (вопрос 11)

| Событие | Параметры |
|---|---|
| `resource_change` | `currency`, `delta`, `balance_after`, `flow` (source/sink), `reason`, `item_id` |

Частые мелкие изменения объединяются в одно событие на уровень или сессию, а не на каждый тап. Балансы в точках прогресса берутся из `level_end` и `session_snapshot`. Цены из конфига — из `ref_price_list` (§4).

### 3.5 Механики возврата (вопрос 8)

| Событие | Параметры |
|---|---|
| `mechanic` | `mechanic` (daily_reward / quest / streak / event / …), `action` (shown / claimed / completed / broken), `streak`, `reward` |
| `notif_scheduled` | `type`, `delay_s` — локальный пуш поставлен в очередь |
| `push_open` | `type`, `campaign_id` (из данных, пришедших в пуше), `age_s` (сколько секунд прошло от доставки пуша до открытия) |

Одно имя события `mechanic` покрывает любые новые механики и не тратит лимит в 500 имён. Витрина сравнивает удержание тех, кому механику показали, и тех, кому нет, **внутри одного слоя глубины** (одинаковые `lvl` и `sn`). Это снижает самоотбор, но не убирает его. Для решений по механике нужен A/B с контрольной группой без механики (Firebase A/B, вопрос 15).

### 3.6 Монетизация (вопросы 13–17)

Здесь — полная модель воронок монетизации. [monetization-attribution.md §4](monetization-attribution.md) ссылается на неё и описывает деньги: источники сумм, net, сверку.

**Поток** — одна возможность купить или посмотреть рекламу: показ оффера, вход в магазин, точка, где могла быть реклама. У потока один ID — `flow_id`.

**Правила `flow_id`:**

- `flow_id` — UUID. Его создаёт открывающее событие потока. Каждый следующий шаг этого потока несёт тот же `flow_id`.
- Открывающие события: `iap_offer_view`, `iap_purchase_start` (если покупка началась вне оффера, например во вкладке магазина), `ad_opportunity`. Они несут контекст: `placement`, `trigger`, `src`, `src_eid`.
- Следующие шаги несут `flow_id`, `placement` и свои поля. `placement` повторяется на каждом шаге: это самый частый срез, и он остаётся, даже если открывающее событие потеряно. `trigger` и `src` берутся из открывающего события соединением по `flow_id`. Шаг, у которого открывающее событие не дошло, считается в `dq`.

**`trigger` и `src`:**

- `trigger` отвечает на один вопрос: кто начал поток. Значения: `user` — игрок сам нажал на вход в этот оффер или рекламу; `auto:<rule_id>` — игра показала его по правилу `rule_id`. ID правил лежат в справочниках значений вместе с остальными списками (ниже).
- `src` — откуда пришёл игрок: ID экрана, `level_end`, `push:<campaign_id>`, `mechanic:<id>`.
- `src_eid` — `eid` события-источника (например, `push_open` или `level_end`), если оно было.
- Пример 1: игрок открыл пуш, и игра автоматически показала оффер → `trigger=auto:<rule_id>`, `src=push:<campaign_id>`.
- Пример 2: игрок нажал баннер магазина на карте → `trigger=user`, `src=map`.

**Бюджет параметров.** У каждого события свои параметры плюс 7 служебных полей (§2.1) — не больше 25. Счёт стоит в последней колонке таблиц.

**Покупки (IAP)**

| Событие | Когда | Параметры | Мест: свои + служебные |
|---|---|---|---|
| `iap_offer_view` | показ оффера; открывает поток | `flow_id`, `offer_id`, `sku`, `placement`, `trigger`, `src`, `src_eid`, `price_local`, `currency`, `offer_n` (какой по счёту показ этого оффера игроку), `soft`, `hard`, `last_result` | 13 + 7 = 20 |
| `iap_offer_close` | оффер закрыт без покупки | `flow_id`, `placement`, `action` (`close` / `back` / `timeout` / `app_background`), `ms_visible` (сколько оффер был на экране) | 4 + 7 = 11 |
| `iap_purchase_start` | игрок начал покупку (вызов стора) | `flow_id`, `placement`, `sku`, `offer_id`; если покупка началась вне оффера, событие открывает поток и несёт ещё `trigger`, `src`, `src_eid` | 7 + 7 = 14 (с полями открытия) |
| `iap_purchase` | стор сообщил об успешной оплате | `flow_id`, `placement`, `sku`, `offer_id` (пустой, если поток открыт вне оффера, например во вкладке магазина), `transaction_id` (iOS — transactionId Apple, Android — `orderId`), `price_local`, `currency`, `redelivered` (1 — транзакция доставлена повторно, 0 — нет) | 8 + 7 = 15 |
| `iap_fail` | покупка не завершилась | `flow_id`, `placement`, `sku`, `reason`, `store_code` (код ошибки стора или Nakama) | 5 + 7 = 12 |
| `iap_granted` | игра выдала покупку после проверки в Nakama | `flow_id`, `placement`, `transaction_id`, `items` (что выдано), `ms_validate` (сколько длилась проверка) | 5 + 7 = 12 |
| `sub_state` | клиент узнал состояние подписки | `sku`, `state` (trial / active / grace / expired / refunded) — это то, что знает клиент; достоверные данные о подписке хранит Nakama | 2 + 7 = 9 |

- Переход к следующему шагу и есть конверсия. Отдельного события «нажал купить» нет: нажатие видно как `iap_purchase_start` в том же потоке.
- `reason` в `iap_fail`: `user_cancel` / `pending` / `deferred` / `store_error` / `network` / `already_owned` / `not_available` / `validation_invalid` (Nakama ответила, что чек недействителен) / `validation_error` (проверку не удалось выполнить). Отдельного события о проверке нет: неудачная проверка — это `iap_fail` с причиной `validation_*`.
- «Оплачено, но не выдано» — `iap_purchase` без `iap_granted` с тем же `transaction_id`.
- Чек, который Nakama уже проверяла, приходит с пометкой `seen_before` [факт по коду Nakama]. Это не ошибка. Если игра ещё не выдала этот `transaction_id` (смотрит в своё сохранение), она выдаёт покупку и пишет `iap_granted`. Если уже выдала, ничего не пишет.

**Повторная доставка транзакции.** Транзакция может прийти позже начала покупки: приложение закрыли после оплаты, покупка ждёт одобрения родителя (Ask to Buy), оплата в ожидании (`pending`). Незавершённую транзакцию стор отдаёт приложению повторно при следующем запуске. На iOS расширение Defold IAP подписывается на очередь платежей StoreKit при старте, а StoreKit держит транзакцию в очереди и отдаёт её подписчику, пока приложение не вызовет `finishTransaction` [факт по коду extension-iap, iap_ios.mm; факт: developer.apple.com/documentation/storekit/skpaymentqueue/finishtransaction(_:)]. На Android расширение при первом `iap.set_listener` запрашивает незавершённые покупки (`queryPurchasesAsync` для разовых покупок и подписок) и отдаёт их в слушатель [факт по коду extension-iap, iap_android.cpp, IapGooglePlay.java]. Приёмка — §7, п. 7. Чтобы она попала в свой поток:

- На `iap_purchase_start` игра добавляет `flow_id` в слот этого SKU в своём сохранении. В слоте одного SKU может быть несколько живых потоков.
- Запись потока удаляется после `iap_granted` или после финального `iap_fail` с причиной `user_cancel`, `already_owned`, `not_available`, `store_error` или `validation_invalid`. При причинах `network`, `validation_error`, `pending`, `deferred` запись остаётся.
- Повторно доставленная транзакция берёт самый старый живой поток своего SKU. Если записи нет, `flow_id` пустой. Случай «транзакция доставлена повторно, а у этого SKU открыт более новый поток» считается в `dq`.
- Такой `iap_purchase` несёт `redelivered = 1`. Доля таких покупок видна в `dq`.

**Реклама (rewarded, interstitial, баннеры)**

| Событие | Когда | Параметры | Мест: свои + служебные |
|---|---|---|---|
| `ad_opportunity` | каждая точка, где могла быть показана rewarded или interstitial реклама; для баннера — место баннера появилось на экране; открывает поток | `flow_id`, `format` (rewarded / interstitial / banner), `placement`, `trigger`, `src`, `src_eid`, `ready` (1 — реклама загружена, 0 — нет заполнения), `blocked` (`cap` / `cooldown` / `none`) | 8 + 7 = 15 |
| `ad_offer_view` | показано предложение посмотреть rewarded рекламу | `flow_id`, `placement`, `reward` (что предложено) | 3 + 7 = 10 |
| `ad_offer_close` | предложение закрыто без просмотра | `flow_id`, `placement`, `action` (`decline` / `close`) | 3 + 7 = 10 |
| `ad_show` | игра вызвала показ | `flow_id`, `placement`, `show_id` | 3 + 7 = 10 |
| `ad_show_fail` | показ не удался | `flow_id`, `placement`, `show_id`, `error_code` | 4 + 7 = 11 |
| `ad_revenue_paid` | колбэк выручки MAX | `flow_id`, `placement` (игры), `show_id`, `ad_unit`, `format`, `network`, `network_placement`, `revenue`, `precision`, `creative_id` | 10 + 7 = 17 |
| `ad_close` | реклама закрыта; для баннера — место баннера ушло с экрана | `flow_id`, `placement`, `format`, `show_id` (кроме баннера), `completed` (только rewarded: 1 — пришёл колбэк ReceivedReward), `ms_on_screen` (от Displayed до Hidden; у баннера — сколько место было на экране); только у баннера: `ad_unit` (ad unit MAX, по которому шёл баннер), `impressions` (сколько колбэков OnBannerAdRevenuePaidEvent пришло за поток), `revenue` (их сумма), `revenue_exact` (сумма тех, где `precision = exact`) | 10 + 7 = 17 |
| `ad_reward_granted` | награда выдана | `flow_id`, `placement`, `show_id`, `reward` | 4 + 7 = 11 |

- Порядок rewarded: `ad_opportunity` → `ad_offer_view` → `ad_offer_close` (только если игрок отказался) → `ad_show` → `ad_show_fail` или `ad_revenue_paid` → `ad_close` → `ad_reward_granted`.
- Порядок interstitial: `ad_opportunity` (с `ready`) → `ad_show` → `ad_show_fail` или `ad_revenue_paid` → `ad_close`.
- Порядок баннера: `ad_opportunity` с `format = banner` (место появилось на экране, `ready` — как у других форматов) → `ad_close` (место ушло с экрана). Один поток — одно появление места на экране, даже если оно длится через полночь.
- Расширение MAX для Defold отдаёт для всех полноэкранных форматов колбэки Displayed, Hidden, DisplayFailed, Clicked, RevenuePaid, а ReceivedReward — только для rewarded [факт по коду расширения]. Поэтому `completed` есть только у rewarded. У interstitial сигнала досмотра нет.
- `show_id` — ID одной попытки показа. После `ad_show_fail` поток может попробовать снова, тогда у новой попытки новый `show_id`. Игра передаёт в MAX `custom_data = show_id` [факт: аргумент есть].
- Поля `ad_revenue_paid` берутся из колбэка выручки расширения AppLovin: revenue, revenuePrecision, networkName, networkPlacement, format, adUnitIdentifier, creativeIdentifier [факт по коду расширения]. `precision` бывает `exact`, `publisher_defined`, `estimated`, `undefined` или пустым [факт: документация AppLovin].
- У баннеров нет события на каждый показ: слишком большой объём ([architecture.md §2.3](architecture.md)). Показы и выручку за поток клиент суммирует в `ad_close`. Итог выручки баннеров по-прежнему берётся из User-Level API. Выручка баннера на поток — сумма клиента `ad_close.revenue`. Доля точной выручки баннеров — `revenue_exact / revenue`.

**Справочники значений.** Списки значений `placement`, `trigger` (вместе с ID правил `auto:<rule_id>`), префиксы `src`, `reason`, `action`, `blocked` лежат в YAML трекинг-плана и попадают в `ref_tracking_plan` (§5). Значение, которого нет в списке, считается в `dq`.

**Деньги потока:**

- Покупки: `iap_purchase.transaction_id` (вместе с `flow_id`) → `fct_iap` ([monetization-attribution.md §4.1](monetization-attribution.md)). `iap_granted` только отмечает выдачу, поэтому «оплачено, но не выдано» остаётся в своём потоке.
- Реклама: строка MAX User-Level API соединяется с потоком по Custom Data = `show_id`. Ветку выбирает загрузчик автоматически, по наличию колонки Custom Data в файле: если колонка есть, строка соединяется с потоком по `show_id`; если нет, выручка потока = `ad_revenue_paid.revenue` (то же значение MAX, но доставленное клиентом). Итог выручки всегда берётся из User-Level API. Как загрузчик читает CSV — [monetization-attribution.md §4.2](monetization-attribution.md). В `dq` видны показы без строки или события выручки.
- Баннеры: выручка потока = `ad_close.revenue` (сумма клиента). Итог — из User-Level API.

**Кто игрок в момент потока.** Состояние игрока в момент оффера пишется в само событие: балансы `soft`, `hard` и последний результат `last_result`; прогресс `lvl` уже есть в служебных полях (§2.1). Остальные признаки игрока берутся соединением таблиц (join) на момент потока: из `dim_player`, `fct_player_day` и последнего `session_snapshot` или `level_end` до потока, но никогда — из события после него.

**Витрины воронок:**

- `offer_funnel` — по каждому `flow_id` оффера или магазина: последний достигнутый шаг, шаг отвала, время между шагами. Срезы: `placement` × `trigger` × `src` × сегмент (платящий или нет, когорта, канал, `lvl`).
- `first_purchase_path` — потоки и шаги игрока до первой покупки.
- `ad_funnel` — по каждому потоку рекламы. Rewarded: возможность → реклама загружена → предложение → согласие → показ → досмотр → награда. Предложение, согласие, досмотр и награда есть только у rewarded. Interstitial: возможность → реклама загружена → показ → ошибка или выручка → закрытие. Баннер: место на экране → место ушло с экрана, с числом показов и выручкой за поток. Плюс выручка на одну возможность. Срезы те же.

**Слабое место.** Связь «поток → деньги» держится на клиентских событиях, а их доставка не гарантирована. Итоги по деньгам от этого не зависят: они приходят от сервера и сторов [вывод]. Слабость мерится в `dq`: доля строк `fct_iap` без потока и доля строк `ad_impressions` без потока по всем форматам. У баннеров строки с потоком по одной не соединяются: проверка сравнивает суммы клиента в `ad_close` с User-Level по игроку × день UTC × ad unit × placement; поток относится ко дню UTC своего `ad_close`, игроко-дни с потоком баннера через полночь UTC в сравнение не входят, их доля показана в `dq`.

### 3.7 Атрибуция (вопросы 1, 2, 4)

`ua_attribution` ([monetization-attribution.md §3.1](monetization-attribution.md)) сводит ключи GCD разных сетей к одним параметрам (`campaign_id`, `adset_id`, `ad`, `ad_id`, `af_siteid` и другие) по таблице сопоставления. Полный JSON GCD хранится в Nakama и попадает в BigQuery, поэтому сеть, которая кладёт свои ID под другими ключами, перекладывается в Dataform без нового билда. Креатив и площадку отдают не все сети: Google App Campaigns креатив на уровне пользователя не передаёт. Поэтому вопрос 4 закрывается только для сетей, которые креатив отдают. Витрина показывает долю установок с известным креативом.

### 3.8 PvP (второстепенный режим)

| Событие | Параметры | Мест: свои + служебные |
|---|---|---|
| `pvp_match_start` | `match_id`, `mode` | 2 + 7 = 9 |
| `pvp_match_end` | `match_id`, `mode`, `result` (win / lose / draw / quit), `dur_s` | 4 + 7 = 11 |

Пока PvP второстепенный, хватает этих двух клиентских событий. Если PvP станет основным циклом игры, результат, рейтинг и силу соперника нужно брать из обработчика матчей Nakama (match handler): он работает на сервере, поэтому данные полные по построению [вывод].

## 5. Самодокументируемая модель (под будущий доступ ИИ через MCP)

Модель описывает себя сама, чтобы позже ИИ-ассистент мог работать с BigQuery через MCP (протокол подключения ИИ к данным).

- У каждой таблицы и колонки в Dataform есть описание (`description` в `columns`); оно попадает в схему BigQuery.
- Описания событий и параметров генерируются из YAML трекинг-плана в таблицу `ref_tracking_plan` (событие, параметр, тип, смысл, допустимые значения, версия плана). Значение параметра вне списка допустимых считается в `dq`.
- Определения метрик (D1, ARPDAU, LTV) лежат в одном месте Dataform и версионируются. На это опирается пометка сопоставимости в §2.3.

## 6. Как позже добавить CPI и затраты без переделок

Для вопросов 3, 13 и расчёта ROAS понадобится таблица `fct_cost_daily`. Ключ строки: `date × platform × country × source × campaign_id × adset_id`. В строке — затраты, показы и клики. Источник — сводные отчёты AppsFlyer или API сетей. Таблица соединяется с игроками по ID кампании и адсета, которые уже есть в `dim_player`. Существующие таблицы при этом не меняются. Ограничение то же, что у каналов: для iOS без ATT стоимость установки считается только в сумме, без привязки к отдельным игрокам.

## 7. Приёмка реализации на тестовом билде

Вопросы схемы закрыты: правила — в §2.1, §3.1, §3.6 и [monetization-attribution.md §3–4](monetization-attribution.md). Этот список проверяет только, что реализация делает то, что написано в документах; ни один пункт не ждёт платного трафика или настоящих покупок. Непрошедший пункт — ошибка реализации, её исправляют.

1. Проверка YAML при сборке проходит; в DebugView каждое событие плана приходит со всеми своими параметрами; ни одно событие не несёт `firebase_error`.
2. Увести игру в фон, выгрузить её из списка приложений, запустить снова → приходит копия `session_snapshot` с `rcv = 1` и `eid` оригинала; `session_begin.prev_end = bg`.
3. Вызвать `crash.write_dump()` из отладочного меню, перезапустить → приходит `app_crash`, `prev_end = crash`. Убить процесс на переднем плане (остановка из Xcode / `adb shell am force-stop`, пока игра на экране), запустить снова → `prev_end = killed_fg`.
4. Установка по тестовой ссылке OneLink (тестовое устройство AppsFlyer) → `ua_attribution` приходит с полями по таблице сопоставления ([monetization-attribution.md §3.1](monetization-attribution.md)); сырой JSON лежит в Nakama, в коллекции `ua_gcd`.
5. Загрузчик MAX: юнит-тест на заголовке из примера документации (с пробелом перед последним именем) и на заголовке с колонками Custom Data и Network — оба разбираются; файл без `User ID` роняет загрузку с ошибкой.
6. iOS-сборка: `plutil` по Info.plist собранного приложения показывает `NSAdvertisingAttributionReportEndpoint`, `AttributionCopyEndpoint` и `SKAdNetworkItems`; интеграционный тест AppsFlyer SDK показывает установку и `af_purchase` с `af_revenue` / `af_currency` (покупка в песочнице); в отладочном логе AppsFlyer SDK видны обновления conversion value после событий из схемы.
7. Покупка в песочнице: закрыть игру после оплаты, до `iap.finish`, запустить снова → `iap_purchase` с `redelivered = 1` и `flow_id` исходного потока (§3.6).
