# Карта данных: 20 вопросов → события, таблицы, витрины

Дополняет [architecture.md](architecture.md) и [monetization-attribution.md](monetization-attribution.md). Здесь — **каталог событий** (§3). Его машинная версия — YAML-файл трекинг-плана в репозитории игры; этот документ описывает тот файл.

**Корень:** на любой из 20 вопросов можно ответить, только если выполнены два условия. Первое: у каждого события и каждого игрока есть одинаковые метки сравнимости — билд, версия конфига, эксперименты, канал, когорта (когорта — группа игроков с общими параметрами установки: датой, платформой, страной, билдом). Второе: у ключевых моментов игры есть снимок состояния игрока. Поэтому план состоит из трёх частей: служебные поля на всех событиях (§2), несколько событий-снимков (§3) и справочники версий (§4).

## 1. Где отвечаем на каждый вопрос

Обозначения:

- **DWH** — ответ считается в хранилище данных BigQuery.
- **AF** — AppsFlyer.
- **консоли** — кабинеты сетей и сторов.
- **позже** — вне текущего решения, но модель к нему готова.

Термины из таблицы:

- **витрина** — готовая таблица с посчитанными метриками, из неё строятся дашборды;
- **слой глубины** — группа игроков, продвинувшихся в игре одинаково (одинаковые `lvl` и `sn`);
- **стандартизация по составу** — пересчёт показателя так, чтобы у сравниваемых каналов состав аудитории считался одинаковым;
- **самоотбор** (selection bias) — механику чаще используют те, кто и так играет усерднее, поэтому связь «механика → удержание» может оказаться кажущейся;
- **A/B с контрольной группой** — часть игроков не получает фичу, результаты двух групп сравнивают;
- **дифф** — список отличий между двумя версиями.

## 2. Метки сравнимости — что есть у каждого события и игрока

### 2.1 На каждом событии (добавляет обёртка `analytics.lua`)

| Поле | Смысл |
|---|---|
| `eid` | ID события: по нему убираются дубли ([architecture.md §2.1](architecture.md)) |
| `seq` | Порядковый номер события на установке: по пропускам в нём видна доля потерянных событий. Пропуск виден, только если после потерянных событий пришло следующее, поэтому это нижняя граница потерь: потерянный хвост (последние события) игрока, который не вернулся, не виден (§3.1) |
| `cts` | Время события на устройстве игрока |
| `build` | Версия билда |
| `cfg` | Версия шаблона Remote Config, с которой играет клиент |
| `sn` | Номер сессии на установке (1 = первая сессия на этой установке). Первая сессия игрока — `sn = 1` на его первой установке (§2.2) |
| `lvl` | Ключевой прогресс (уровень или глава) |

Эти 7 полей занимают 7 из 25 мест под параметры события. На смысловые параметры остаётся 18. Группы A/B Firebase ставит сам как user property (свойство игрока, не события) `firebase_exp_<id>`. Места в параметрах события они не занимают [факт].

### 2.2 На игроке (`dim_player`, вычисляется в DWH)

- **Когорта:** дата установки, платформа, страна, билд установки, `cfg` установки — по первой установке игрока.
- **Канал:** `ua_source`, `ua_campaign_id`, `ua_adset_id`, `ua_ad_id`, `ua_site_id`, `attribution_quality`. Храним **ID**, а не только имена: имена кампаний меняют, ID нет. По этим же ID будет считаться будущая таблица затрат (§6). Канал берётся из первой установки игрока (с самым ранним первым событием). Если у неё нет `ua_attribution`, канал — «неизвестно».
- **Аккаунт:** тип входа (`gamecenter` / `google` / `device`), дата привязки.
- **Эксперименты:** все группы A/B с датой попадания. Firebase назначает группу установке, а не игроку: вариант считается по ID эксперимента и ID установки Firebase [факт]. После переустановки или на втором устройстве игрок может попасть в другую группу. Группа игрока — его первое назначение. Игроки, у которых в одном эксперименте больше одной группы, учитываются отдельно и исключаются из `ab_results` и `ab_monetization`; их доля видна в `dq` (проверках качества данных). Серверная выручка игрока относится к его группе.
- **Тест:** `test_id` из реестра `ref_tests`, если установка попала в окно теста.

У одного игрока может быть несколько установок: переустановка, второе устройство. Каждая установка — строка в `dim_install` (одна строка на `user_pseudo_id`: `player_id`, время первого события, билд, поля `ua_attribution`). Поздняя установка из новой кампании — это повторное привлечение: она видна в `dim_install` и не перезаписывает когорту и канал в `dim_player`. Первая сессия игрока — `sn = 1` на его первой установке. По ней считаются вопросы 1, 6 и 7.

### 2.3 Реестр тестов `ref_tests` (ответ на вопрос 19)

Небольшая таблица в репозитории Dataform (инструмент, который собирает таблицы в BigQuery из кода). Задаётся YAML или CSV и превращается в таблицу. Заполняется руками при запуске каждого теста:

| Поле | Пример |
|---|---|
| `test_id`, `name` | `sl_ph_2026_11`, «Софт-ланч Филиппины, ноябрь» |
| `start`, `end` | даты окна установок |
| `geos`, `platforms`, `sources` | `PH`; `android`; `applovin, mintegral` |
| `builds`, `experiments` | диапазон билдов; ID A/B-тестов |
| `variants` | значения параметров Remote Config в каждом варианте эксперимента: `0` (контроль) — `pack_price = 4.99`, `1` — `pack_price = 2.99`; записываются при запуске теста (§4) |
| `tracking_plan_version` | версия YAML трекинг-плана |
| `notes`, `comparable_with` | что меняли; с какими тестами корректно сравнивать |

Витрины считаются по меткам когорты, поэтому любой тест можно сравнить с любым другим. Дашборд показывает рядом с цифрами `tracking_plan_version` и зрелость когорты (сколько времени прошло с установки). Если у сравниваемых тестов разные версии трекинг-плана или разные определения метрик (§5), сравнение помечено как несопоставимое, а не молча смешано.

## 3. Каталог событий

Имена событий короткие. Событий мало, параметров много. Новое имя заводится, только если параметры существующего события не закрывают вопрос.

### 3.1 Сессия и техника (вопросы 6, 18)

| Событие | Когда | Параметры |
|---|---|---|
| `session_begin` | старт или возврат из фона | `start` (cold/warm), `net` (wifi/cell/none), `load_ms`, `bg_s` (сколько был в фоне) |
| `load_step` | только холодный старт, по шагам загрузки | `step` (boot / firebase / auth / config / assets / first_frame), `ms`, `ok`, `err` |
| `session_snapshot` | уход в фон (событие окна Defold `FOCUS_LOST` / `ICONIFIED`) | `dur_s`, `last_action`, `last_screen`, `soft`, `hard`, `energy`, `goal_id`, `goal_pct`, `last_result`, `rewards_pending`, `notif_next` (тип ближайшего локального пуша) |
| `app_crash` | при следующем запуске, если Defold `crash.load_previous()` вернул дамп (данные о сбое) | `signal`, `crash_build`, `crash_ts` |
| `app_error` | нефатальная ошибка | `code`, `where` |
| `auth` | вход в Nakama | `method` (gamecenter/google/device), `ok`, `is_new`, `err` |
| `account_link` | привязка Game Center / Google к анонимному аккаунту | `method`, `ok`, `conflict` (аккаунт уже был у другого профиля) |

События, записанные при уходе в фон, Firebase хранит на устройстве и отправляет при следующем запуске [факт для SDK]. Какая доля теряется при принудительном завершении приложения — **не проверено**; мерится через `seq`. У вернувшегося игрока потерянный `session_snapshot` виден как пропуск в `seq` перед следующим `session_begin`. У игрока, который не вернулся на D1, такая потеря не видна. Поэтому доля потерь хвоста (сессий, у которых пропали последние события) считается по вернувшимся игрокам и переносится на не вернувшихся как оценка. Краш до инициализации Firebase в DWH не виден. Такие краши видны только суммарно: в Android Vitals и Xcode Organizer. Поэтому Firebase инициализируется первым.

### 3.2 Онбординг и навигация (вопрос 9)

| Событие | Параметры |
|---|---|
| `tutorial_step` | `step_id`, `step_idx`, `ms_prev` (от предыдущего шага), `skipped` |
| `screen` | `screen_id`, `from`, `ms_prev` |

«Значимое действие» задаётся флагом в YAML трекинг-плана (например: `level_start`, `item_upgrade`, `tutorial_step`), а не в коде клиента. Витрина `time_to_next_action` считает медиану и хвост (самые долгие случаи) времени от каждого экрана или шага до следующего значимого действия.

### 3.3 Прогресс и баланс (вопросы 7, 10)

| Событие | Параметры |
|---|---|
| `level_start` | `level_id`, `mode`, `attempt`, `power` (сила игрока по формуле игры), `difficulty` (из конфига), `boosters_pre` |
| `level_end` | `level_id`, `attempt`, `result` (win/lose/quit), `dur_s`, `score` или `stars`, `progress_pct`, `fail_reason`, `power`, `difficulty`, `boosters_used`, `continue_used`, `soft`, `hard` |
| `item_upgrade` | `item_id`, `from_lvl`, `to_lvl`, `cost`, `currency`, `power_after`, `after_loss` (1, если прошлый уровень проигран) |

Поля `power` и `difficulty` показывают механизм — почему игроки отваливаются, а не только где (правило «где ≠ почему»). Формулу `power` геймдизайн фиксирует до первого билда. Без неё вопрос 10 закрывается только наполовину.

### 3.4 Экономика (вопрос 11)

| Событие | Параметры |
|---|---|
| `resource_change` | `currency`, `delta`, `balance_after`, `flow` (source/sink), `reason`, `item_id` |

Частые мелкие изменения объединяются в одно событие на уровень или сессию, а не на каждый тап. Балансы в точках прогресса берутся из `level_end` и `session_snapshot`. Цены из конфига — из `ref_price_list` (§4).

### 3.5 Механики возврата (вопрос 8)

| Событие | Параметры |
|---|---|
| `mechanic` | `mechanic` (daily_reward / quest / streak / event / …), `action` (shown / claimed / completed / broken), `streak`, `reward` |
| `notif_scheduled` | `type`, `delay_s` — локальный пуш поставлен в очередь |
| `push_open` | `type`, `campaign_id` (из данных, пришедших в пуше), `age_s` (сколько секунд прошло от доставки пуша до открытия) |

Одно имя события `mechanic` покрывает любые новые механики и не тратит лимит в 500 имён. Витрина сравнивает удержание тех, кому механику показали, и тех, кому нет, **внутри одного слоя глубины** (одинаковые `lvl` и `sn`). Это снижает самоотбор, но не убирает его. Для решений по механике нужен A/B с контрольной группой без механики (Firebase A/B, вопрос 15).

### 3.6 Монетизация (вопросы 13–17)

Как в [monetization-attribution.md §4](monetization-attribution.md), с дополнениями:

| Событие | Параметры |
|---|---|
| `iap_offer_view` | `offer_id`, `sku`, `placement`, `trigger`, `price_local`, `currency`, `offer_n` (какой по счёту показ этого оффера игроку), `soft`, `hard`, `last_result` |
| `iap_purchase_start` / `iap_purchase` / `iap_fail` | `sku`, `offer_id`, `placement`, `transaction_id` (iOS — transactionId Apple, Android — `orderId`), `purchase_ctx_id`, `price_local`, `currency`, `reason` |
| `sub_state` | `sku`, `state` (trial / active / grace / expired / refunded) — это то, что знает клиент; достоверные данные о подписке хранит Nakama |
| `ad_offer_view` / `ad_show` / `ad_reward_granted` | `show_id`, `format`, `placement`, `trigger`, `reward` |

Состояние игрока в момент оффера пишется в само событие: балансы `soft`, `hard` и последний результат `last_result`; прогресс `lvl` уже есть в служебных полях (§2.1). На оффере 10 своих параметров и 7 служебных — 17 из 25. Более подробный контекст берётся соединением таблиц (join) из последнего `level_end` / `session_snapshot` до оффера, но никогда — из события после него.

### 3.7 Атрибуция (вопросы 1, 2, 4)

`ua_attribution` ([monetization-attribution.md §3](monetization-attribution.md)) получает дополнительные поля `ad_id`, `af_siteid`. Креатив и площадку отдают не все сети: Google App Campaigns креатив на уровне пользователя не передаёт. Поэтому вопрос 4 закрывается только для сетей, которые креатив отдают. Витрина показывает долю установок с известным креативом.

## 4. Справочники версий (вопросы 11, 12, 19)

| Таблица | Источник | Что даёт |
|---|---|---|
| `dim_build` | YAML в репозитории: билд, дата релиза, платформа, список изменений | Метки релизов на графиках |
| `dim_config_version` | Remote Config REST API: список версий шаблона и их содержимое; задание запускается ежедневно [факт: API есть] | Дифф параметров между версиями `cfg`: что именно поменялось. Значения, заданные как варианты A/B, в выгруженный шаблон не входят [факт]; они берутся из `ref_tests` (§2.3) |
| `ref_price_list` | Таблица цен из конфига баланса, по версии `cfg` и варианту эксперимента (цены вариантов — из `ref_tests`) | Прайс, с которым сравнивается баланс игроков |
| `dim_player_experiment` | user properties `firebase_exp_<id>` из экспорта | Группы A/B у каждого игрока: группа игрока — первое назначение; игроки с несколькими группами в одном эксперименте помечены и исключены из итогов A/B (§2.2) |
| `ref_tests` | YAML в репозитории Dataform (§2.3) | Реестр тестов для сквозного сравнения |

Витрина `release_impact` показывает метрики когорт до и после каждого изменения `build` или `cfg` и дифф конфига. Если в одном релизе поменялось много всего, витрина покажет совпадение во времени, но не причину. Для крупных изменений баланса действует правило: раскатывать через Remote Config на часть игроков или как A/B. Тогда вклад каждого изменения можно измерить.

## 5. Самодокументируемая модель (под будущий доступ ИИ через MCP)

Модель описывает себя сама, чтобы позже ИИ-ассистент мог работать с BigQuery через MCP (протокол подключения ИИ к данным).

- У каждой таблицы и колонки в Dataform есть описание (`description` в `columns`); оно попадает в схему BigQuery.
- Описания событий и параметров генерируются из YAML трекинг-плана в таблицу `ref_tracking_plan` (событие, параметр, тип, смысл, версия плана).
- Определения метрик (D1, ARPDAU, LTV) лежат в одном месте Dataform и версионируются. На это опирается пометка сопоставимости в §2.3.

## 6. Как позже добавить CPI и затраты без переделок

Для вопросов 3, 13 и расчёта ROAS понадобится таблица `fct_cost_daily`. Ключ строки: `date × platform × country × source × campaign_id × adset_id`. В строке — затраты, показы и клики. Источник — сводные отчёты AppsFlyer или API сетей. Таблица соединяется с игроками по ID кампании и адсета, которые уже есть в `dim_player`. Существующие таблицы при этом не меняются. Ограничение то же, что у каналов: для iOS без ATT стоимость установки считается только в сумме, без привязки к отдельным игрокам.

## 7. Что проверить на первом тестовом билде

1. Доходит ли `session_snapshot`, записанный при уходе в фон, если игру затем выгрузили из памяти (проверять по `seq`).
2. Отдаёт ли `crash.load_previous()` дамп после краша на iOS и Android.
3. Есть ли в GCD AppsFlyer (данные об источнике установки, которые AppsFlyer передаёт в игру) поля креатива и `af_siteid` у ваших сетей закупки.
4. Входят ли default-параметры (которые Firebase добавляет сам) в лимит 25. Бюджет в §2.1 посчитан для худшего случая, когда входят: 7 служебных полей плюс 18 смысловых. Если не входят, свободных мест будет больше.
