# DWH для мобильной игры на Defold: Firebase/GA4 → BigQuery → BI

Пометки:
- **[факт]** — взято из официальной документации или кода;
- **[не проверено]** — нужно проверить на тестовом проекте до запуска;
- **[вероятно]**, **[широко известно]** — официального подтверждения нет, но так следует из документации или опыта рынка;
- **[оценка]** — приблизительная цифра.

DWH — хранилище данных для аналитики. BigQuery — облачная база данных Google, куда GA4 выгружает события игры.

## 0. Главное в трёх пунктах

1. **Лимит 1M событий в день касается не кастомных (своих) событий, а ежедневной выгрузки в BigQuery (batch: раз в сутки пачкой). Туда по смыслу документации входят все события, включая автоматические** (прямо Google этого не пишет).
   - При 20–30k DAU (активных игроков в день) лимит кончается уже на 33–50 событиях на игрока в день.
   - После этого Google **ставит ежедневную выгрузку на паузу, и пропущенные дни не догружаются** [факт].
   - Streaming-выгрузка (события поступают непрерывно) лимита не имеет и стоит $0.05/GB (~600k событий на GB, то есть ~$5–15/мес на вашем объёме) [факт].
   - Но Google её только «старается доставить» (best-effort): возможны дыры и дубли.
   - **Решение:** основной источник — streaming. Каждое событие несёт свой ID `eid` и порядковый номер `seq`. Поэтому потери и дубли становятся измеряемым числом, а не слепой верой.
2. **GA4 нельзя считать источником правды о деньгах и атрибуции.**
   - В BigQuery не попадают возвраты (refund) [факт].
   - Тестовые покупки и покупки из песочницы Google отбрасывает, но фрод (мошеннические покупки) с джейлбрейков проходит.
   - Автоматический `ad_impression` (показ рекламы) из AdMob в BigQuery не выгружается [факт].
   - Атрибуции (определения, из какой рекламной сети пришла установка) по сетям, кроме Google, и по SKAN (SKAdNetwork, способ атрибуции установок на iOS от Apple) в GA4 нет.
   - Решения масштаба >$100k/мес опираются на **сверенные** деньги:
     - серверная валидация чеков;
     - уведомления сторов о возвратах;
     - выручка с рекламы из отчёта MAX по каждому показу;
     - ежедневная сверка с отчётами сторов и медиации.
   - Атрибуция остаётся в AppsFlyer (MMP — сервис, который определяет источник установки). Затраты и ROAS (окупаемость рекламных затрат) в текущее решение не входят. DWH не дублирует MMP (подробно — [monetization-attribution.md](monetization-attribution.md)).
3. **Корень задачи:** нужна выручка и поведение по когортам с известной полнотой и точностью. Сам по себе экспорт GA4 этого не даёт. Поэтому схема строится вокруг **собственного контракта событий** (правил, какие события игра логирует и с какими параметрами) **и контроля качества**. GA4 в ней — только бесплатный способ доставки данных, который можно заменить.

## 1. Схема

```
 ИГРА (Defold)
 ├─ analytics.lua  ── обёртка: eid, seq, cts, base-параметры
 │     └─ extension-firebase-analytics ──► Firebase/GA4 property (часовой пояс = UTC)
 │                                             └─ BigQuery export: STREAMING (+daily, пока < 1M)
 ├─ nakama-defold ── вход: Game Center / Google Play Games / анонимный device ──► NAKAMA: player_id = user_id
 ├─ extension-iap  ── чек/токен покупки ──► NAKAMA: проверка в сторе ──► выдача покупки
 ├─ extension-applovin (MAX) ── set_user_id(player_id), custom_data = show_id ──► событие ad_show (контекст)
 └─ DefAppsFlyer (свой аккаунт, Growth) ── conversion data ──► событие ua_attribution

 NAKAMA (свой сервер, ~$5/мес)
          покупки, подписки, возвраты (уведомления Apple ASSN V2 и Google RTDN приходят в Nakama)
          └─ ночная выгрузка изменённых строк (cron на сервере) ──► bq.nakama_purchases, nakama_subscriptions, nakama_users
 СТОРЫ:   Play Console → GCS-отчёты; App Store Connect Sales/Finance ──► bq.store_reports (сверка, net-коэффициент)
 MAX:     User-Level Ad Revenue API (D+1) ──► bq.ad_impressions; Revenue Reporting API ──► сверка
 FIREBASE: Remote Config REST API (версии шаблона) ──► bq.dim_config_version
 ЗАТРАТЫ / ROAS: вне текущего решения (можно добавить позже, не меняя модель)

 BigQuery (один проект, один регион)
   raw_ga4 (экспорт, только чтение)
     └─► Dataform (бесплатно, по расписанию ежедневно + пересчёт последних 3 дней)
          landing_events   — своя копия, MERGE по eid (не зависим от жизненного цикла таблиц Google)
          stg_events       — плоская, типизированная, без дублей; partition by date, cluster by event_name, user_id
          core:  dim_player · fct_sessions · fct_iap (валидированные, net) · fct_subscriptions · fct_ad_revenue · fct_player_day
          marts: kpi_daily · cohort_retention · ltv_curves · funnel_ftue · progression · economy · монетизация · ab_results
          dq:    assertions + dq_daily (полнота, дубли, свежесть, сверки) — блокируют витрины при провале
   └─► Data Studio (бывший Looker Studio, бесплатно) — читает ТОЛЬКО витрины
       (+ Metabase OSS — когда понадобится самообслуживание для >1 аналитика)
```

Расшифровки к схеме и дальнейшему тексту:

- **IAP** — покупки внутри приложения. **MAX** — AppLovin MAX, медиация (сервис, который выбирает рекламу из разных сетей).
- **ASSN V2** (Apple) и **RTDN** (Google) — уведомления сторов о покупках, подписках и возвратах.
- **GCS** — Google Cloud Storage, облачное хранилище файлов. **cron** — запуск по расписанию.
- **D+1** — данные приходят с задержкой в один день. **net** — выручка за вычетом комиссии стора.
- **MERGE** — команда SQL: объединяет новые данные с таблицей по ключу, поэтому строка с уже имеющимся `eid` не добавляется второй раз.
- **partition by date** — таблица хранится частями по датам. **cluster by** — внутри частей данные упорядочены по указанным полям. Оба приёма уменьшают объём данных, который читает запрос.
- **stg** — промежуточная очищенная таблица. **core** — основные таблицы: `dim_` — справочники, `fct_` — факты. **marts** (витрины) — готовые сводные таблицы для дашбордов.
- **assertions** — автоматические проверки данных в Dataform. **dq** (data quality) — слой проверок качества данных.
- **funnel_ftue** — воронка первого пользовательского опыта (FTUE, first-time user experience).

Оставлен как запасной путь (§6) |

| Своя `landing_events` + MERGE по `eid` | Streaming может дублировать и терять события. Поведение intraday-таблиц (внутридневных таблиц streaming) без ежедневной выгрузки не гарантировано | Чтение `events_intraday_*` напрямую из BI: дорого и ненадёжно |

Velir/dbt-ga4 (готовый пакет для GA4) заточен под веб-сессии. Scheduled queries (запросы по расписанию в BigQuery): нет графа зависимостей и тестов |
| Data Studio на маленьких витринах | 0 ops (не нужно администрирование); бесплатно; стоимость под контролем, если графики читают агрегаты размером в мегабайты | Grafana — для технических (ops) метрик, не для когорт и воронок. Superset — тяжёл в сопровождении. BI Engine (платное ускорение запросов BigQuery) — ~$300/мес |
| Серверная валидация + сверка со сторами | Только так видны возвраты и фрод, а выручка совпадает с выплатами | Клиентский `in_app_purchase` как источник правды |
| Nakama (open source, heroiclabs) как бэкенд | Из коробки есть: аккаунты с входом через Game Center / Google / устройство, проверка покупок и подписок, приём уведомлений о возвратах. Есть клиент для Defold. Свой код валидации не пишем | Firebase (Auth + Firestore + Cloud Functions): нет матчмейкинга (подбора соперников) и живого PvP (игрок против игрока), нет SDK для Defold — клиент и всю серверную логику писали бы сами. RevenueCat для покупок: 1% выручки выше $2 500/мес, а Nakama проверяет покупки бесплатно. PlayFab: официальный Lua SDK не развивается (репозиторий в архиве с 2022), всё пришлось бы писать через REST. Unity Gaming Services: нет Defold. Свой сервис на Cloud Run: всё писать самим |

## 2. Контракт событий (самая важная часть)

### 2.1 Обёртка `analytics.lua` — единая точка логирования

Каждое событие проходит через одну функцию, которая добавляет служебные параметры:

| Параметр | Зачем |
|---|---|
| `eid` — UUID события | В схеме экспорта нет ID события [факт]. `eid` — ключ дедупликации (удаления дублей) streaming-выгрузки |
| `seq` — счётчик на установку, монотонный, хранится в сейве | Дыры в `seq` = доля потерянных событий. Это единственный способ измерить полноту, которую Google не гарантирует |
| `cts` — клиентское время, мс | `event_timestamp` в документации описан как время получения [факт, формулировка менялась]. Офлайн-события приходят позже, поэтому нужно клиентское время |
| `build`, `cfg` (версия remote config / баланса) | Сравнение релизов и откат конфигурации |
| `sn` — номер сессии на установке | Первая сессия и глубина без джойнов (объединений таблиц) |
| `lvl` / ключевой прогресс | Срезы любого события по прогрессу без джойнов |

Параметры, которые меняются редко, задаются через `set_default_event_parameters` (есть в Lua API расширения [факт]) и обновляются при изменении.

**Бюджет лимитов** [факт]:

- 25 параметров на событие (имя события и имя параметра — до 40 символов, значение — до 100 символов);
- ≤500 разных имён событий;
- 25 user properties (свойств пользователя; имя ≤24, значение ≤36 символов).

Служебные параметры занимают 7 мест из 25, на смысловые остаётся 18. Расчёт исходит из того, что default-параметры тоже входят в лимит 25 — **[не проверено]**.

Правило: **мало имён, много параметров**. Новое имя события заводится только тогда, когда новые параметры на существующем событии не закрывают вопрос.

### 2.2 Каталог событий

Каталог и связь каждого события с 20 вопросами владельца — в [tracking-plan.md](tracking-plan.md). Здесь только правила, которые нельзя нарушать:

- Покупка логируется как `iap_purchase`, **не** `in_app_purchase`: иначе получим дубль с автоматическим событием [факт].
- Выручка с рекламы не пишется в события: она приходит из MAX API и соединяется с показами по `show_id`. Баннеры не логируются.
- Навигация — своё событие `screen`: автоматический `screen_view` в Defold почти бесполезен (в Android игра — одна Activity, то есть один системный экран).
- На событиях прогресса нужны поля механики (сила игрока, сложность). Иначе видно только, где игроки уходят, но не почему.

**`user_id`** в Firebase = `player_id` (ID аккаунта Nakama), один во всех SDK (см. §4 и [monetization-attribution.md §2](monetization-attribution.md)).

Трекинг-план хранится в репозитории как YAML-файл. Это единственный источник правды для Lua-констант, staging-модели и проверки дрейфа схемы (расхождения фактических событий с планом).

### 2.3 Бюджет объёма

Не логировать действия покадрово или потапно: сводка по уровню вместо каждого хода. Целевой ориентир — 40–100 событий на DAU в день. Streaming-выгрузка снимает жёсткий потолок, но объём всё равно стоит денег и раздувает хранение.

## 3. Подводные камни и решения

| # | Подводный камень | Последствие | Решение |
|---|---|---|---|
| 1 | Лимит 1M/день на ежедневную выгрузку, в него входят и автоматические события [вероятно; Google прямо не пишет] | Пауза выгрузки, потерянные дни не догружаются [факт] | Streaming как основной источник; `landing_events` — своя копия |
| 2 | Streaming best-effort: дыры, дубли [факт] | Тихая недостача / завышение | `eid` → MERGE; `seq` → доля потерь в `dq_daily` (порог 1%) |
| 3 | В streaming нет `traffic_source` для новых пользователей [факт] | Нет канала установки | Канал из GCD (Get Conversion Data — данные об источнике установки, которые AppsFlyer передаёт игре) через событие `ua_attribution` и user properties |
| 4 | Ежедневная таблица переписывается задним числом до 72 ч; офлайн-события приходят позже [факт; документы расходятся: 2 и 3 дня] | Вчерашние цифры «плывут» | Пересчёт последних 3 дней при каждом прогоне. Когорта (игроки одного дня установки) считается зрелой для метрики дня N (например, удержания D7) через N+3 дня после установки: N дней на саму метрику и 3 дня на запоздавшие события |
| 5 | Нет выгрузки за время до подключения | Данные до подключения экспорта в BigQuery не попадут никогда | Подключить экспорт **до** первого игрока, в том числе на тестах |
| 6 | Смена часового пояса property (ресурса GA4) пропускает день выгрузки [факт] | Даты съезжают, дыра в данных | Выставить UTC до подключения экспорта и не менять |
| 7 | Регион датасета нельзя сменить [факт] | Миграция = копирование всего | Выбрать один раз (US или EU), всё остальное — в том же регионе |
| 8 | В sandbox BigQuery (режиме без подключённой оплаты) таблицы истекают через 60 дней, streaming нет [факт] | Потеря истории | Сразу включить Blaze (платный тариф Firebase) и billing; бюджетные оповещения; квоты на запросы |
| 9 | `user_pseudo_id` меняется при переустановке [широко известно; официально не прописано] | Завышенный DAU и новые установки, заниженное удержание | `user_id` = аккаунт Nakama с тихим входом через Game Center / Google Play Games (§4) |
| 10 | В Lua API Defold нет Consent Mode (режима учёта согласия на сбор данных), только `set_enabled` [факт] | Важно только для EU | Сейчас вне рамок; при выходе в EU — доработка нативного кода расширения |
| 11 | В BigQuery нет возвратов [факт]; клиентские данные о покупках пропускают фрод; на Android автоматическое событие `in_app_purchase` в Defold не подтверждено [не проверено] | Завышенный LTV (выручка с игрока за всё время), ошибка в масштабировании | Проверка покупок в Nakama (Defold отдаёт чек/токен покупки: receipt/purchaseToken [факт]); возвраты через уведомления сторов в Nakama; `fct_iap` = только проверенные покупки минус возвраты |
| 12 | `event_value_in_usd`: курс и момент конвертации не документированы [факт] | Искажения LTV из-за валют | Хранить price_local + currency; конвертировать по своей таблице курсов на дату платежа |
| 13 | Автоматический `ad_impression` не выгружается в BigQuery [факт]; клиентские события о выручке теряются при потерях streaming | Нет полного рекламного LTV | Выручка из MAX User-Level Ad Revenue API по `player_id` (User Id в MAX) |
| 14 | Выручка MAX частично оценочная | Расхождение с выплатами | Ежедневная сверка с MAX Revenue Reporting API; помесячная калибровка при необходимости |
| 15 | GA4 не атрибутирует Meta, Unity, AppLovin, SKAN | Нет канала у игрока | Атрибуция — в AppsFlyer; в DWH только канал как атрибут из GCD, с флагом качества |
| 16 | Канал из GCD неточен; на iOS без разрешения ATT (App Tracking Transparency — запрос на отслеживание) установка выглядит как «органика» [факт] | Ложные выводы по каналам | `attribution_quality`; срезы по каналам — только Android и iOS с ATT; еженедельная сверка с AppsFlyer |
| 17 | Тестовый трафик и устройства QA | Загрязнение когорт | Отдельный Firebase-проект для dev/QA-билдов |
| 18 | Каждый график Data Studio — отдельный запрос в BigQuery; кэш до 12 ч [факт] | Счёт за BigQuery от одного дашборда | BI читает только витрины; `requirePartitionFilter` (запрос обязан указать даты); квоты `QueryUsagePerDay`; maximum bytes billed (предел данных на один запрос) |
| 19 | Materialized views (автоматически обновляемые сохранённые запросы) не работают на wildcard-таблицах (запросах по шаблону имён, например `events_*`) [факт] | — | Инкрементальные таблицы Dataform |
| 20 | Сессии нельзя суммировать по дням; ключ сессии = (user, `ga_session_id`) [факт] | Завышение числа сессий | Сессии считаются в `fct_sessions` за весь диапазон |
| 21 | Хранение растёт (~8 GB/день сырых данных при 5M событий) | Через полгода десятки $/мес | Физическая (сжатая) модель тарификации хранения; срок жизни сырых GA4-таблиц 60–90 дней после переноса в landing; long-term тариф −50% после 90 дней |
| 22 | Ошибки разметки в новых билдах | Тихий слом метрик | `dq`: события на DAU по `build`; неизвестные имена и параметры против YAML-плана |

## 4. Идентичность и когорты

- **Игрок** = `player_id` = ID аккаунта Nakama. Тот же ID служит Firebase `user_id`, MAX User Id и AppsFlyer CUID. На нём считаются удержание, LTV, экономика и A/B.
- **Вход без кнопок** (тихий, без действий игрока):
  - iOS: тихий вход в Game Center → Nakama проверяет подпись Apple и выдаёт аккаунт. Готового расширения Defold, которое отдаёт подпись Game Center, нет. Нужен форк `britzl/extension-gamekit` с одной функцией (примерно 100 строк Objective-C).
  - Android: тихий вход Google Play Games (официальный `extension-gpgs`) → вход Google в Nakama.
  - Игрок не вошёл в Game Center / Play Games: создаётся анонимный аккаунт Nakama по случайному ID устройства, который хранится в сохранении. Позже его можно привязать к Game Center / Google, прогресс сохраняется.
  - Слабое место: анонимный игрок без привязки теряет аккаунт при удалении игры и в DWH становится новым игроком. Доля таких игроков видна в `dim_player.account_type`. Сейчас это не закрываем. Позже можно закрыть без переделок: хранить ключ анонимного аккаунта в iCloud key-value storage, тогда он переживёт переустановку.
- **Первый запуск без сети:** события до входа в Nakama идут без `user_id`. В DWH их привязывает к игроку `user_pseudo_id` из первого успешного события `auth`.
- **Установка** = `user_pseudo_id`. Число установок и атрибуция — в AppsFlyer. CPI (цена установки) и ROAS — вне текущего решения.
- `dim_player` (справочник игроков) хранит:
  - дату первого появления;
  - первые страну, платформу, билд и `cfg`;
  - канал установки с флагом качества;
  - тип аккаунта;
  - payer-флаг (признак платящего игрока);
  - группы экспериментов.

  Полный список — [tracking-plan.md §2.2](tracking-plan.md).
- Правила когорт (по уроку аудитов soft launch, то есть тестового запуска игры):
  - органика (неплатные установки) — отдельный сегмент;
  - незрелые когорты помечены;
  - у каждой цифры есть «штамп базы»: n (число игроков), источник, дата данных.

## 5. Контроль качества — условие «данные для решений»

Assertions в Dataform **блокируют обновление витрин**. На дашборде всегда видны «данные на» и статус сверок.

| Проверка | Порог (стартовый, калибруется) |
|---|---|
| Свежесть landing | < 30 ч |
| Потери по `seq` (по зрелым дням) | < 1% |
| Дубли по `eid` после MERGE | 0 |
| Объём событий по каждому `event_name` против среднего за 7 дней | ±30% → оповещение |
| IAP: валидированные против отчётов сторов (день × страна × SKU, то есть товар в сторе) | ±2–3% |
| Реклама: MAX User-Level против MAX Revenue Reporting | ±2% |
| Показы MAX без User Id / покупки без `player_id` | ≈0 |
| Установки: `ua_attribution` против агрегатов AppsFlyer (еженедельно) | расхождение задокументировано и стабильно |
| Неизвестные события и параметры против YAML | 0 новых без записи в плане |

## 6. Запасной путь (если слабое место подтвердится)

Слабое место схемы — streaming-выгрузка без гарантий полноты. Убрать его в рамках бесплатного GA4 нельзя. Схема его **измеряет** (`seq`) и изолирует: всё, что ниже `landing_events`, зависит от нашего контракта событий, а не от схемы GA4.

Если потери стабильно выше 1–2%, ключевые события (покупки, уровни, ресурсы) дублируются в свой коллектор. Естественное место для него — уже работающая Nakama. У неё есть приём событий от клиента и серверные хуки на них [не проверено, есть ли нужный хук для пачек событий]. Дальше события идут в BigQuery через Storage Write API (первые 2 TiB/мес бесплатно [факт]). Меняется только слой landing.

Цена этого пути: офлайн-буфер, ретраи (повторные отправки) и защита эндпоинта (адреса приёма событий) на стороне клиента.

## 8. Порядок внедрения

1. **До первого игрока:**
   - проект GCP (Google Cloud) + billing + бюджетные оповещения;
   - Firebase prod и dev отдельно;
   - property в UTC;
   - выбор региона;
   - экспорт (streaming + daily);
   - квоты на запросы.
2. **Клиент:**
   - вход в Nakama (§4);
   - `analytics.lua` (eid/seq/cts/base);
   - трекинг-план YAML по [tracking-plan.md](tracking-plan.md);
   - `player_id` во всех SDK;
   - проверка в DebugView (инструмент Firebase, где события видны сразу).

   Проверить пункты, помеченные **[не проверено]**: авто-события и `in_app_purchase` в Defold; поведение intraday-таблиц без daily; выгрузку кастомного `ad_impression`; входят ли default-параметры в лимит 25.
3. **Dataform:** landing → stg → core → kpi_daily, cohort_retention, funnel_ftue + dq.
4. **Деньги:** проверка покупок и подписок в Nakama + уведомления сторов в Nakama + ночная выгрузка таблиц Nakama; GCS-отчёты Play + ASC (App Store Connect) Sales/Finance; курсы валют; `fct_iap`; MAX User-Level API → `fct_ad_revenue` + сверка (детали — [monetization-attribution.md](monetization-attribution.md)).
5. **Атрибуция:** событие `ua_attribution`; еженедельная сверка с агрегатами AppsFlyer.
6. **A/B:** группы берутся из user property `firebase_exp_<id>` (индекс варианта, '0' = контроль [факт]). Из них `ab_results` считает результаты со своей проверкой SRM и доверительными интервалами. SRM (sample ratio mismatch) — расхождение размеров групп с заданными долями. Firebase A/B сам проверку SRM не делает.

## 9. Вводные и ограничения

- Медиация — AppLovin MAX. Трафик закупается в любых рекламных сетях. Все аккаунты (сторы, MAX, AppsFlyer) свои.
- MMP — AppsFlyer Growth без ROI360 и Data Locker. ROAS, CPI и затраты в DWH не считаются, модель к ним готова ([tracking-plan.md §6](tracking-plan.md)).
- EU consent (согласие пользователей из EU) вне рамок.
- Бэкенд — Nakama: в игре есть живое PvP.
- Вход: Game Center (iOS) и Google Play Games (Android) без кнопок, анонимный аккаунт как запасной. Сторонних соцсетей нет.
- Покупка выдаётся только после проверки на сервере. Подписки поддерживаются.

**Слабое место Nakama — свой сервер.** Если Nakama недоступна, не работают вход, PvP и выдача покупок. Деньги при этом не теряются: непроверенная покупка остаётся незавершённой, и стор отдаёт её игре снова. Убрать слабое место можно только managed-хостингом Nakama (сервером управляет провайдер), а он дороже цели. Поэтому риск снижается так:
- ежедневный бэкап Postgres (базы данных Nakama) в Cloud Storage с проверкой восстановления;
- внешняя проверка доступности (Cloud Monitoring uptime check) с оповещением;
- обновления Nakama — сначала на тестовом сервере;
- свежесть выгрузки `nakama_*` в BigQuery проверяется в `dq`.
