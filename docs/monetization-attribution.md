# Монетизация и атрибуция в DWH

Дополняет [architecture.md](architecture.md). Пометки:

- **[факт]** — проверено по документации или коду расширения;
- **[не проверено]** — проверить до запуска (документация, тестовая сборка, песочница), никогда не на живом трафике;
- **[проверить]** — проверить до запуска (документация, тестовая сборка, песочница), никогда не на живом трафике;
- **[широко известно]** — официального подтверждения нет, но так следует из документации или опыта рынка;
- **[оценка]** — оценка по указанному источнику;
- **[вывод]** — следует из проверенных фактов, но отдельно не проверялось;
- **[не найдено]** — официального ответа нет; рядом сказано, что верно при любом ответе.

**Вводные:**

- Рекламная медиация — AppLovin MAX (одна платформа, через которую показывается реклама разных сетей). Берём сети из топ-10. Трафик закупаем в любых сетях.
- Паблишера нет: все аккаунты (сторы, MAX, AppsFlyer) свои.
- AppsFlyer — MMP (сервис, который определяет, из какой рекламы пришла установка). Тариф Growth (pay-as-you-go, оплата по факту использования): без ROI360 (платный модуль AppsFlyer для учёта рекламной выручки и окупаемости) и без Data Locker (выгрузки сырых данных по каждой установке).
- **ROAS (окупаемость рекламных затрат) и затраты в DWH не считаем**; модель позволяет добавить их без переделок ([tracking-plan.md §6](tracking-plan.md)).
- Согласие пользователей ЕС (EU consent) не нужно.

## 0. Корень задачи и граница

**Корень:** нужна полная картина денег и поведения **по каждому игроку**: сколько он принёс через IAP (покупки в приложении) и рекламу, за что и когда заплатил, как играл до и после. Источники разные: стор (магазин приложений), MAX, клиент (игра на устройстве). Поэтому всё упирается в **один ID игрока во всех SDK** и в сверку каждого денежного потока с его источником правды.

**Граница с MMP — дубль не строим:**

| Вопрос | Где отвечаем | Почему |
|---|---|---|
| Установки, атрибуция (откуда пришёл игрок), SKAN (SKAdNetwork — механизм Apple для атрибуции iOS-установок без привязки к пользователю), постбэки (сообщения рекламным сетям об установках и событиях); ROAS — в той мере, в какой его покажет AppsFlyer и кабинеты сетей | **AppsFlyer / кабинеты сетей** | Это работа MMP. Без сырых данных её не повторить, а ROAS не входит в текущее решение |
| Из чего складывается выручка, кто платит, за что, когда; поведение; внутриигровая экономика; A/B; LTV-кривые по сегментам (накопленная выручка на игрока по дням после установки) | **DWH** | В MMP этого нет или есть только поверхностно |
| Канал установки | В DWH — **только как атрибут игрока** (поле в его профиле) для срезов поведения и монетизации | Не для расчёта ROAS и не для подсчёта установок |

В DWH нет ни своей загрузки затрат, ни своего ROAS по кампаниям, ни своей SKAN-логики. Если ROAS понадобится позже, добавим таблицу затрат и агрегаты AppsFlyer. Текущие таблицы менять не придётся (`dim_player`, `ltv_curves` уже есть).

## 1. Схема потоков

```
                      player_id (ID аккаунта Nakama) ── один ключ во всех SDK
                                │
 ИГРА (Defold) ─────────────────┼──────────────────────────────────────────────────
  Nakama    вход через Game Center / Google / ID устройства → player_id
  Firebase  set_user_id(player_id)      → события поведения + контекст покупок/рекламы
  AppsFlyer set_customer_user_id(...)   → атрибуция в AppsFlyer; GCD (данные атрибуции на устройстве) → событие ua_attribution
  MAX       set_user_id(player_id)      → User Id в отчёте о выручке по каждому показу
  IAP       чек/токен ──────────────────► Nakama: проверка в сторе → выдача покупки → finish (завершение транзакции)
 ──────────────────────────────────────────────────────────────────────────────────
 NAKAMA
  проверенные покупки и подписки; уведомления Apple (ASSN V2) и Google (RTDN) → refund_time / состояние подписки
  ночная выгрузка по расписанию (cron на сервере) → nakama_purchases, nakama_subscriptions, nakama_subscription_events, nakama_users
 API (ежедневные задания Cloud Run Jobs)
  MAX User-Level Ad Revenue API (данные на следующий день, D+1) → ad_impressions (выручка по каждому показу + player_id)
  MAX Revenue Reporting API                  → ad_revenue_agg     (сверка)
  App Store Server API Get Transaction Info (по transactionId) → apple_transactions (цена и валюта iOS)
  App Store Connect Sales/Finance, Play GCS  → store_reports      (сверка + net за единицу iOS)
  Google Play Orders API (по orderId)        → store_orders       (сумма покупок Android: gross и net)
  Курсы валют                                → fx_daily
 ──────────────────────────────────────────────────────────────────────────────────
 DWH (Dataform)
  fct_iap (gross/net USD: цена для покупателя / выплата стора; без тестов, минус возвраты) · fct_ad_revenue · dim_player · fct_player_day
  → витрины монетизации (§5) → Data Studio
```

## 2. Идентичность — фундамент «360»

**Порядок инициализации** (иначе часть выручки останется без игрока):

1. Первым инициализируется Firebase: иначе не будет видно игроков, у которых загрузка сломалась до входа в аккаунт.
2. Вход в Nakama: сохранённая сессия → тихий вход через Game Center / Google Play Games → анонимный аккаунт по ID устройства. `player_id` = ID аккаунта Nakama. Схема входа — [architecture.md §4](architecture.md).
3. `firebase analytics.set_user_id(player_id)` [факт: API есть].
4. `applovin.set_user_id(player_id)` — **до инициализации MAX** [факт]. MAX инициализируется после входа: реклама в первые секунды не показывается, а без интернета её всё равно нет.
5. `appsflyer.set_customer_user_id(player_id)` задаёт CUID (customer user id — ID игрока в AppsFlyer). Вызывать на каждом холодном старте (запуске приложения с нуля) до `start_sdk`: SDK7 (седьмая версия AppsFlyer SDK) CUID не сохраняет [факт]. Запуск AppsFlyer **не ждёт** входа в Nakama дольше пары секунд. На iOS перед запуском AppsFlyer идёт запрос ATT: запрос ATT → `start_sdk` → GCD → `ua_attribution`. В DefAppsFlyer (в нём iOS SDK 7.0.2) нет ни функций ожидания ATT, ни самого запроса ATT: запрос показывает отдельное расширение Defold, а `start_sdk()` документация велит вызывать после запроса [факт по коду и документации DefAppsFlyer]. Нативный AppsFlyer iOS SDK 7 ответа ATT не ждёт: `waitForATTUserAuthorization` устарел, и если `start` вызван до ответа, данные установки уходят без IDFA, поэтому держать `start` до ответа должно само приложение [факт: dev.appsflyer.com/hc/docs/migrate-ios-sdk-to-v7]. Когда показывать запрос ATT, решает геймдизайн. Игра держит `start_sdk` до ответа, а ожидание обязательно ограничено таймером от холодного старта: через N секунд после запуска приложения (число задаёт геймдизайн) игра вызывает `start_sdk`, даже если ответа нет, с `att_status` = `not_determined`. Таймер не зависит от того, показан ли запрос и закончилась ли сессия. Если игрок ответил раньше, `start_sdk` вызывается сразу после ответа. Так AppsFlyer запускается и у игроков, ушедших в первой сессии. Качество канала у них такое же, как без ATT (`attribution_quality`, §3.2). Без Data Locker CUID нужен только для поиска игрока в интерфейсе AppsFlyer. Канал в DWH приходит из GCD на устройстве.
6. Покупки проверяются в Nakama от имени этого же аккаунта.

Переустановка не делит игрока надвое, если он вошёл через Game Center или Play Games. Анонимный игрок без привязки после переустановки становится новым. Долю таких игроков показывает `dim_player.account_type`.

У одного игрока может быть несколько установок. Их хранит `dim_install`: одна строка на `user_pseudo_id` с полями `player_id`, время первого события, билд, поля `ua_attribution`. Первая установка — с самым ранним первым событием. Когорта и канал игрока берутся из неё. Если у первой установки нет `ua_attribution`, канал игрока остаётся «неизвестно»: канал поздней установки на него не переносится. Поздняя установка с новой кампанией — повторное привлечение: она видна в `dim_install` и `dim_player` не перезаписывает. Первая сессия игрока — `sn = 1` на первой установке.

Проверки качества данных (`dq`):

- доля показов рекламы без User Id — цель ≈0;
- доля покупок без `player_id` — цель ≈0;
- доля игроков с больше чем одним `user_pseudo_id` (ID установки в Firebase; несколько значит переустановки) — цель: величина известна и стабильна.

## 3. Атрибуция в DWH: канал как атрибут игрока

### 3.1 Источник

Единственный бесплатный путь — **GCD (conversion data callback)**: AppsFlyer на устройстве сообщает игре данные атрибуции. DefAppsFlyer (расширение AppsFlyer для Defold) отдаёт весь нативный словарь как JSON [факт]. Игра логирует событие `ua_attribution` в Firebase:

| Параметр | Из GCD |
|---|---|
| af_status | Organic / Non-organic (установка без рекламы / с рекламы) |
| media_source, campaign_id, campaign, adset_id, adset, ad | Канал и кампания (параметр события вмещает имена до 100 символов) |
| install_time, is_first_launch | Время установки и признак первого запуска |
| att_status (из игры) | Ответ игрока на запрос ATT (запрос Apple на отслеживание на iOS): authorized / denied / not_determined |

В user properties (свойства игрока в Firebase) кладём только короткие значения: `ua_source`, `ua_campaign_id`. Значение user property — не больше 36 символов [факт]. Имена кампаний длиннее этого лимита и в user property обрежутся.

### 3.2 Ограничения (принимаем осознанно)

| Ограничение | Последствие | Как с этим работаем |
|---|---|---|
| AppsFlyer сам называет атрибуцию по данным SDK наименее точным методом. GCD может прийти до завершения атрибуции [факт] | Часть платных установок в DWH окажется органикой | Сверка с AppsFlyer (§3.3); канал в DWH — для срезов, не для подсчёта |
| iOS без ATT (в играх разрешение даёт ~35–40% игроков [оценка по отчёту Adjust]) атрибутируется только через SKAN: агрегированно, без привязки к пользователю [факт] | В DWH большая часть платных iOS-установок выглядит органикой | Поле `attribution_quality`: `device` / `restricted` / `no_att_unknown`. На iOS без ATT канал = «неизвестно», а **не** «органика». Исключение — Apple Ads (реклама в App Store): AppsFlyer атрибутирует её детерминированно (по токену Apple, без IDFA), отдельно от SKAN и независимо от ATT [факт: support.appsflyer.com/hc/en-us/articles/213747963]. Установки с `media_source` Apple Ads и без ATT сохраняют канал, `attribution_quality = device` |
| Media source (источник трафика) принимает значение `restricted` при Aggregated Advanced Privacy (режим AppsFlyer, в котором данные по iOS-установкам без согласия на трекинг отдаются только в сумме) или ограничениях партнёра (рекламной сети) [факт] | Канал скрыт | Отдельное значение, не смешивать с органикой |
| Android: атрибуция Meta требует Meta Install Referrer и принятых условий AMM (Advanced Mobile Measurement — соглашение Meta о передаче данных атрибуции) [факт] | Без этого Meta на Android тоже частично «органика» | Включить в AppsFlyer (§7) |

**Вывод:** срезы по каналам в DWH достоверны для **Android**, для **iOS с ATT** и для Apple Ads на iOS. Для iOS в целом правильные разрезы — платформа × страна × неделя установки. Остальные каналы iOS без ATT видны только в SKAN-отчётах AppsFlyer.

### 3.3 Сверка с AppsFlyer (без сырых данных)

Раз в неделю сравниваем установки в DWH (по `ua_attribution`) с агрегированным отчётом AppsFlyer в разрезе media_source × платформа × страна × неделя. Базовый процесс — сверка вручную по дашборду. Доступ к API у AppsFlyer — платная (premium) функция; на Growth есть пробный период 30 дней [факт: страница тарифов]. Aggregate Pull API используем, только если его купим.

Расхождение фиксируем как известную величину. Если оно резко меняется, значит что-то сломалось в SDK или в настройках.

**Правило одного источника:** число установок и атрибуция по кампаниям берутся из AppsFlyer; структура выручки и поведение — из DWH. В одном отчёте их не смешиваем без пометки.

## 4. Монетизация

### 4.1 IAP

**Поток** (покупка выдаётся только после проверки на сервере):

1. Defold IAP возвращает транзакцию. На iOS (StoreKit 1 — прежний API покупок Apple) в ней `trans_ident` и чек. На Android — `purchaseToken` (`receipt`) и `orderId` (`trans_ident`) [факт]. Nakama хранит в `transaction_id` покупки: на iOS — transactionId Apple (= `trans_ident`), на Android — `purchaseToken`. Своей колонки для `orderId` нет, он лежит только в JSON `raw_response` (ответ стора) [факт по коду Nakama]. Автозавершение покупки (auto-finish) в Defold IAP **выключено**.
2. Клиент отправляет чек в Nakama через методы клиента nakama-defold, которые проверяют покупки и подписки Apple / Google.
3. Nakama проверяет покупку в сторе, сохраняет её у аккаунта игрока и отвечает. Повторная отправка того же чека помечается `seen_before` [факт по коду Nakama]. Игра выдаёт покупку и вызывает `iap.finish`. На Android покупку обязательно подтвердить в течение 3 дней, иначе Google вернёт деньги [факт].
4. Клиент пишет Firebase-событие `iap_purchase` (стор сообщил об успешной оплате) с `transaction_id` = `trans_ident` (на iOS — transactionId Apple, на Android — `orderId`) и полями `flow_id`, `placement`, `sku`, `offer_id`, `price_local`, `currency`, `redelivered`. `flow_id` — ID одной возможности покупки: его создаёт открывающее событие (`iap_offer_view` или `iap_purchase_start`), и его несут все следующие шаги. После выдачи покупки игра пишет `iap_granted` с тем же `transaction_id`; ошибки оплаты и проверки — `iap_fail` с `reason`. «Оплачено, но не выдано» = `iap_purchase` без `iap_granted`. Шаги воронки, их поля и правило для повторно доставленных транзакций — [tracking-plan.md §3.6](tracking-plan.md). `purchaseToken` в событие не кладём: он длиннее лимита параметра события в 100 символов [широко известно]. Цена и валюта берутся из `iap.list`: у каждого товара есть `price` (число), `price_string` (строка для показа) и `currency_code` на iOS и в Google Play [факт по коду расширения: `src/iap_ios.mm`, `IapGooglePlay.java`]. Эта цена — запасной источник суммы и контекст поведения. Цена из каталога (`iap.list`) может отличаться от списанной: скидки, вводные предложения.
5. Ночная выгрузка переносит изменённые строки таблиц покупок и подписок Nakama в BigQuery. Откуда что берём: факт и статус покупки — из Nakama; сумма покупки — из стора по каждой транзакции (ниже); источник правды по деньгам — отчёты сторов. Ключ соединения (JOIN) клиентского события с покупкой Nakama: на iOS — `transaction_id` (= `trans_ident`); на Android — `orderId` (клиентский `trans_ident`), со стороны Nakama его берём из `raw_response`.

**Два ограничения Nakama, проверенные по исходникам:**

- **Nakama не хранит цену и валюту покупки.** Поэтому сумму каждой покупки берём из стора. Откуда взята сумма, показывает поле `fct_iap.amount_source`:
  - `store_order` (Android): ежедневное задание читает Google Play Developer API Orders (`orders.get` / `orders.batchget`) по `orderId`. Gross (цена для покупателя) = `total`: сколько заплатил покупатель, с учётом скидок и налогов. Net (выплата) = `developerRevenueInBuyerCurrency`: за вычетом комиссий, налогов и частичных возвратов. Там же есть налог (`tax`) и события возврата [факт]. Суммы приходят в валюте покупателя, в USD переводим по `fx_daily`.
  - `store_transaction` (iOS): ежедневное задание вызывает App Store Server API Get Transaction Info (`GET /inApps/v1/transactions/{transactionId}`) по `transaction_id` каждой новой iOS-покупки из `nakama_purchases` и пишет результат в `apple_transactions`. Метод работает для любого ID транзакции и любого типа покупки, в том числе для уже завершённой (finished) [факт: developer.apple.com/documentation/appstoreserverapi/get-transaction-info]. Из подписанной транзакции (JWS) берём `price` / 1000 (Apple отдаёт цену в тысячных долях; цена учитывает скидку оффера подписки), `currency` (код ISO 4217), `storefront` (страна витрины App Store), `offerType` (тип оффера) [факт: developer.apple.com/documentation/appstoreserverapi/jwstransactiondecodedpayload]. `price` — сумма за всё купленное количество [факт: developer.apple.com/documentation/appstoreserverapi/price]; расширение defold/extension-iap на iOS всегда ставит `payment.quantity = 1` (`src/iap_ios.mm`, `IAP_Buy`) [факт по коду расширения], поэтому `price` — цена одной единицы [вывод]. Поля выплаты (net) в транзакции нет; включён ли в цену налог, Apple не пишет [факт]. Почему задание, а не хук Nakama: Defold IAP на iOS работает через StoreKit 1 и отдаёт только чек приложения, без JWS [факт по коду расширения]. Такой чек Nakama проверяет через `verifyReceipt`; в его ответе цены нет, и строка покупки в Nakama цену и валюту не хранит [факт по коду Nakama]. Хук уведомлений Apple для разовой покупки не срабатывает: он вызывается только на возврат [факт по коду Nakama]. Значит, цену не получает ни хук проверки, ни хук уведомлений, и её надо запросить у Apple отдельно [вывод]. Для задания нужен ключ In-App Purchase API (§7).
  - `client_event`: стор сумму не дал, берём цену из клиентского `iap_purchase`.
  - `missing`: суммы нет нигде. Такие строки остаются в `fct_iap` с пометкой и никогда не считаются нулём. Доля `missing` по платформам — в `dq`.

  Сверка со сторами (§5 architecture.md) ловит расхождения.
- **Чеки StoreKit 1 Nakama проверяет через `verifyReceipt`.** Defold IAP на iOS отдаёт только чек приложения, поэтому другого пути проверки сейчас нет [факт по коду расширения и Nakama]. Apple объявила `verifyReceipt` устаревшим в 2023 году, но метод отвечает, а дату отключения Apple не назвала и обещала предупредить заранее [факт: developer.apple.com/forums/thread/731550]. Если дату объявят, проверку переносим на Get Transaction Info по `transactionId`: это серверный запрос к Apple с подписанным ответом, чек для него не нужен [вывод]. Подписанные транзакции StoreKit 2 (формат JWS) Nakama проверяет без `verifyReceipt` [факт по коду Nakama]. Если расширение Defold IAP перейдёт на StoreKit 2, Nakama сама переключится на проверку JWS.

**Возвраты и подписки:**

- **Apple:** App Store Server Notifications V2 (ASSN V2, уведомления Apple о событиях покупки) настраиваются на адрес Nakama. Nakama записывает `refund_time` у покупки и обновляет состояние подписки [факт].
- **Google:** Real-time Developer Notifications (RTDN, уведомления Google о событиях покупки) приходят через Pub/Sub (сервис сообщений Google Cloud) push-запросом на адрес Nakama [факт: обработчик есть]. Пропущенные уведомления Nakama повторно не запрашивает, а часть ошибок записи подтверждает ответом HTTP 200, поэтому стор их больше не пришлёт [факт по коду Nakama]. Ежедневное задание постоянно сверяет Voided Purchases API (список возвращённых покупок, окно 30 дней) с таблицей Nakama.
- **История подписок:** у подписки в Nakama одна строка на `original_transaction_id` (исходный ID транзакции). При каждом продлении строка перезаписывается (`expire_time`, `raw_response`, `raw_notification`), отдельной таблицы продлений нет [факт по коду Nakama]. Поэтому серверный хук Nakama на уведомления сторов (`RegisterSubscriptionNotificationApple` / `RegisterSubscriptionNotificationGoogle`; хук получает тип уведомления, подписку и ответ стора [факт по коду Nakama]) дописывает каждое уведомление в свою таблицу `nakama_subscription_events`. Строки в ней только добавляются и не меняются: тип уведомления, ID транзакции, исходный ID транзакции, продукт, начало и конец периода, `orderId` продления (Android), окружение (`environment`), исходное уведомление целиком. Таблица уходит в BigQuery с ночной выгрузкой.
  - Android: в ответе Google по подписке (v2) списанной суммы нет. Есть `lineItems[].latestSuccessfulOrderId` — `orderId` последнего оплаченного продления [факт по коду Nakama]. Хук сохраняет его в каждой строке, а сумму продления берёт задание Orders API (`store_order`, выше) по этому `orderId`. `recurringPrice` из того же ответа — цена плана без скидок и налогов [факт], для выручки её не используем.
  - iOS: хук уведомлений Apple по подписке получает расшифрованную транзакцию (`TransactionInfo`) с полями `Price`, `Currency`, `Storefront`, `OfferType` [факт по коду Nakama]. Хук пишет их в каждую строку `nakama_subscription_events`, так что сумма продления iOS приходит вместе с уведомлением.
- В DWH: `fct_iap` = проверенные покупки без `environment = SANDBOX` (тестовых), возвраты вычитаются по `refund_time`. `fct_subscriptions` строится из `nakama_subscription_events`: периоды подписок с состояниями (триал, активна, grace — отсрочка при неудачном списании, истекла, возврат) и выручка продлений.

**Gross → net (от цены для покупателя к выплате стора) — главный источник ошибки в LTV:**

- Цена для покупателя включает НДС. Выплата от стора НДС не включает [факт для Apple].
- Комиссия Apple — 15% в Small Business Program (до $1M), иначе 30%.
- Подписки Apple: вне Small Business Program доля разработчика растёт с 70% до 85% после года оплаченной подписки; в программе — 85% с самого начала [факт]. В отчёте продаж Apple эта ставка видна по полю Proceeds Reason (значение `Rate After One Year`), поэтому выплата за единицу из строки с нужным Proceeds Reason её уже учитывает (выбор строки — ниже) [вывод].
- **Комиссии Google Play в 2026 году меняются по рынкам и датам: 10–25% плюс отдельный сбор за биллинг в части стран** [факт; таблица комиссий сложная].
- Поэтому фиксированный процент не используем. Net каждой покупки берём из стора. Откуда взят net, показывает поле `fct_iap.net_source`:
  - `store_order` (Android): net из Orders API (выше).
  - `sales_report_unit` (iOS): выплата за единицу из ежедневного отчёта продаж App Store Connect (Sales report, тип SUMMARY). В отчёте есть Developer Proceeds (per unit) — выплата разработчику за единицу, Customer Price (per unit) — цена для покупателя с налогом, Customer Currency, Currency of Proceeds (валюта выплаты), Country Code (двухбуквенный код страны), SKU, Units (отрицательное значение — возврат), Proceeds Reason, Promo Code, Order Type (оффер подписки или код предложения) [факт: developer.apple.com/help/app-store-connect/reference/summary-sales-report]. Отчёт агрегированный, ID транзакции в нём нет [факт]. Поэтому net каждой продажи iOS ищется среди строк отчёта так:
    1. Кандидаты — строки продаж (Units > 0) за день отчёта × SKU × страну. День отчёта — дата покупки в часовом поясе отчёта: отчёты Apple считаются по тихоокеанскому времени (Pacific Time) [факт: developer.apple.com/help/app-store-connect/measure-app-performance/download-and-view-reports]. Страна — `storefront` из `apple_transactions` (трёхбуквенный код), переведённый в двухбуквенный Country Code. Возвраты приходят из Nakama по `refund_time`.
    2. Остаются кандидаты с тем Proceeds Reason, который ожидается у транзакции. У разовой покупки он пустой. У автопродляемой подписки — `Rate After One Year`, если оплаченный срок подписки игрока больше года, иначе пустой. Оплаченный срок — сумма оплаченных периодов с исходной транзакции по `nakama_subscription_events` [вывод; правило Apple — факт: Summary Sales Report].
    3. Отбор по офферу. Покупка без оффера (`offerType` пустой) — остаются строки с пустым Order Type. Покупка с оффером — строки с непустым Order Type; если у одной из них Order Type совпадает с `offerIdentifier` (промо-оффер, код предложения, win-back) или с `Pay Up Front` / `Pay As You Go` по `offerDiscountType` (вводный оффер), остаётся она. В Order Type у промо-оффера — ID оффера, у кода предложения и win-back — название оффера из App Store Connect, у вводного оффера — `Pay Up Front` или `Pay As You Go`; `offerIdentifier` есть у всех типов офферов, кроме вводного; значения `offerDiscountType`: `FREE_TRIAL`, `PAY_AS_YOU_GO`, `PAY_UP_FRONT`, `ONE_TIME` [факт: Summary Sales Report, JWS]. Совпадения строк Apple не обещает [факт]; без совпадения дальше решает шаг 4, поэтому неверного net не бывает: в худшем случае `ambiguous` [вывод]. Бесплатный пробный период (`offerDiscountType = FREE_TRIAL`): выплаты нет, net = 0, строка отчёта не ищется [вывод]. Колонку Promo Code для отбора не используем: в ней промокоды и пометки вроде подарка (`GP`), которые из JWS не выводятся [факт: Summary Sales Report].
    4. Net назначается, только если у всех оставшихся кандидатов одно значение Developer Proceeds (per unit). Иначе `net_source = ambiguous`. Если кандидатов нет — `missing`.

    Net = Developer Proceeds (per unit) в Currency of Proceeds, в USD по `fx_daily` [вывод].
  - `ambiguous`: у оставшихся кандидатов разные значения выплаты за единицу. Net не назначается.
  - `missing`: подходящей строки нет. Такие строки остаются в `fct_iap` без net.

  Значения `net_source`: `store_order` / `sales_report_unit` / `ambiguous` / `missing`. Доли `ambiguous` и `missing` по платформам — в `dq`.
- Раз в месяц сумма net iOS сверяется с финансовым отчётом Apple (Financial report) за тот же фискальный месяц Apple. Фактические выплаты есть только в нём; суммы в USD в Sales and Trends — оценка [факт: developer.apple.com/help/app-store-connect/reference/financial-report-fields].
- Слабое место: в USD переводим по `fx_daily`, а не по курсу, по которому Apple делает выплату: в финансовом отчёте колонки курса нет [факт]. Остаток расхождения между net за единицу (в USD по `fx_daily`) и финансовым отчётом не сводится к курсу. Apple называет и другие причины расхождений между отчётами: сроки обработки и закрытия периода, границы фискальных периодов, неполученные платежи [факт: developer.apple.com/help/app-store-connect/measure-app-performance/differences-in-reporting-tools]. Поэтому остаток показываем как необъяснённый; курсовая разница — одна из его известных частей.
- Apple прямо пишет, что цена в JWS — не источник для сверки выручки; источник правды — отчёты App Store Connect [факт]. Схема устроена так же.

**Валюты:** храним `price_local` + `currency`. В USD переводим по `fx_daily` на дату платежа. Источник курсов должен покрывать все валюты сторов. ECB (Европейский центральный банк) публикует 29 валют [факт: ecb.europa.eu]. В отчётах Apple 43 валюты, и среди них есть отсутствующие у ECB: AED, SAR, KZT, VND, CLP, COP, PEN, QAR, TZS, EGP, NGN, PKR, TWD [факт: developer.apple.com/help/app-store-connect/reference/reporting/financial-report-regions-and-currencies]. Поэтому одного ECB мало. Больше валют покрывают Open Exchange Rates (200+), ExchangeRate-API (~160) и currencylayer (168) [факт по страницам сервисов]; выбор источника за владельцем. Правило верно для любого источника: если курса валюты на дату платежа нет, сумма в USD остаётся пустой (NULL), а в `dq` срабатывает оповещение (§5 architecture.md); подставной курс не используется.

### 4.2 Реклама (MAX)

**Источник правды по выручке — MAX User-Level Ad Revenue API** (выручка по каждому показу), `aggregated=false` [факт]:

- Поля: время показа, ad unit, формат, placement, страна, сеть, выручка (USD), **User Id** (= `player_id`), IDFA/IDFV, **Custom Data** (произвольное значение, которое игра передаёт вместе с показом). Колонки точности выручки (`precision`) и ID показа нет [факт]. Custom Data есть в списке полей API [факт]; приходит ли она в выгружаемом CSV, не подтверждено. Схема верна при любом ответе: без колонки выручка потока берётся из `ad_revenue_paid.revenue`, итог — по-прежнему из User-Level ([tracking-plan.md §3.6, §7](tracking-plan.md)).
- Данные за день появляются на следующий день после 08:00 UTC. Доступны за последние 45 дней [факт].
- Цену, условия доступа и лимиты запросов страница API не называет [не найдено]; доступ — по Report Key. Схема от ответа не зависит: это вопрос стоимости, его проверить в аккаунте MAX до запуска. Финальная ли это выручка или оценка — не указано; часть выручки в данных — оценка MAX, а не фактическая сумма: например, по ставкам Meta [факт].

**Что это даёт:**

- Сумма выручки по каждому показу приходит с сервера MAX, а не из клиентских событий. Поэтому итог по рекламе не зависит от потерь при streaming-выгрузке (Firebase → BigQuery в реальном времени), и итог выручки баннеров тоже не зависит от клиентских событий.
- Показ соединяется с игровым контекстом. При вызове `show_rewarded_ad` / `show_interstitial` игра передаёт `custom_data = show_id` [факт: аргумент есть]. `show_id` — ID одной попытки показа: после `ad_show_fail` та же возможность может попробовать показ снова, уже с новым `show_id`.

**Клиентские события рекламы.** Поток открывает `ad_opportunity` (точка, где реклама могла быть показана; создаёт `flow_id`). Все шаги несут `flow_id`, шаги показа — ещё и `show_id`. Поля и правила — [tracking-plan.md §3.6](tracking-plan.md).

- Rewarded (видео за награду): `ad_opportunity` → `ad_offer_view` (игроку показано предложение посмотреть rewarded) → `ad_offer_close` (только если игрок отказался) → `ad_show` → `ad_show_fail` или `ad_revenue_paid` → `ad_close` → `ad_reward_granted`.
- Interstitial (полноэкранная реклама): `ad_opportunity` → `ad_show` → `ad_show_fail` или `ad_revenue_paid` → `ad_close`.
- Баннер: один поток на появление места баннера на экране. `ad_opportunity` с `format = banner` → `ad_close`, когда место ушло с экрана. `ad_close` баннера несёт `ms_on_screen`, `impressions` (сколько колбэков OnBannerAdRevenuePaidEvent пришло за поток), `revenue` (их сумма) и `revenue_exact` (сумма тех, где `precision = exact`). Событий на каждый показ баннера нет: их было бы слишком много (бюджет объёма — [architecture.md §2.3](architecture.md)).
- Досмотр (`ad_close.completed`) есть только у rewarded. Расширение MAX для Defold отдаёт для всех полноэкранных форматов Displayed, Hidden, DisplayFailed, Clicked, RevenuePaid, а ReceivedReward — только для rewarded [факт по коду расширения]. У interstitial сигнала досмотра нет.

`ad_revenue_paid` игра пишет для rewarded и interstitial из колбэка выручки MAX с полями `flow_id`, `placement`, `show_id`, `ad_unit`, `format`, `network`, `network_placement`, `revenue`, `precision`, `creative_id`. Событие связывает поток с деньгами и даёт `precision`; источник суммы выручки в DWH всё равно User-Level API.

**Связь потока с деньгами:** строка User-Level соединяется с показом по Custom Data = `show_id`. Если Custom Data в CSV нет, выручка на поток = `ad_revenue_paid.revenue` (то же значение MAX, но доставленное клиентом), а User-Level API остаётся источником итоговой суммы. В `dq` — доля показов без строки выручки или без `ad_revenue_paid`. У баннера выручка на поток — сумма клиента `ad_close.revenue`; итог выручки баннеров — из User-Level API.

**Точность выручки:** колбэк MAX отдаёт `revenuePrecision` [факт по коду расширения]. Значения: `exact` — фактический итог аукциона в реальном времени, `publisher_defined` — цена, заданная издателем, `estimated` — оценка (Auto-CPM и часть сетей с bidding, например Meta), `undefined` или пусто [факт: документация AppLovin]. Bidding сам по себе не означает `exact`. В User-Level API этой колонки нет, поэтому точность берём из клиента: у rewarded и interstitial — из `ad_revenue_paid`, у баннеров — долю `revenue_exact / revenue` из `ad_close`. В `dq` — доля выручки по `precision` в разрезе сети (rewarded и interstitial) и доля точной выручки баннеров.

**Задание:** каждый день в 09:00 UTC загружаем данные за вчера (D-1) и повторно за D-2 и D-3. Каждый загруженный день заменяется целиком: строки за дату × приложение × платформу удаляются и вставляются заново. MERGE (сопоставление новых строк с уже загруженными) не подходит: у MAX User-Level API нет уникального ID показа [факт], сопоставлять не по чему. Если задание падает и никто не замечает больше 45 дней, данные пропадут навсегда. Алерт на свежесть (оповещение, если данные давно не обновлялись) обязателен.

**Сверка полноты загрузки:** сравниваем сумму `ad_impressions` с MAX Revenue Reporting API (`estimated_revenue` в разрезе день × страна × сеть × формат) [факт]. Допуск ±2%. Отдельная метрика — доля показов без User Id.

### 4.3 Что игра отправляет в AppsFlyer (для оптимизации сетей, не для DWH)

DWH от этого не зависит. Но без этих событий сети не смогут оптимизировать закупку на выручку:

- **ROI360 не нужен.** В DefAppsFlyer нет `logAdRevenue` [факт]. Поэтому игра отправляет рекламную выручку обычным событием с `af_revenue` через `log_event` [факт: API есть]. Сумма берётся из колбэка (функции обратного вызова) `On*AdRevenuePaidEvent` в MAX. Отправлять нужно сводкой — за сессию или каждые N минут, — а не на каждый показ: так событий меньше. Если позже подключить ROI360, это событие нужно выключить, иначе выручка задвоится.
- **IAP** — событие `af_purchase` с `af_revenue` / `af_currency` [факт], **после** серверной проверки: AppsFlyer сам покупки не валидирует.
- **SKAN conversion values** (числа, которыми приложение сообщает Apple о поведении игрока): в Lua API для них функций нет [факт]. Если схема настроена в SKAN Conversion Studio, SDK выставляет conversion values сам, без кода; условия — свежая версия SDK и отсутствие в приложении другого SDK, который выставляет conversion values [факт: support.appsflyer.com/hc/en-us/articles/4403727223185]. `log_event` в DefAppsFlyer вызывает нативный `logEventWithEventName` [факт по коду расширения], поэтому события из схемы доходят до нативного SDK [вывод]. Доходят ли постбэки, видно только на устройстве: проверка до запуска — [tracking-plan.md §7](tracking-plan.md), п. 6.
- **Минимум событий:** покупка, рекламная выручка, завершение туториала, 2–3 вехи прогресса. Платны ли in-app события на Growth, страница цен не говорит [не найдено]: на ней оплачиваются конверсии, органика бесплатна [факт: appsflyer.com/pricing]. Спросить AppsFlyer до запуска; ответ влияет на стоимость, а не на данные.
- **Тариф:** Zero не подходит. Он меряет только клики и показы, без атрибуции, и для платного трафика непригоден [факт]. Подходит Growth: 12k конверсий бесплатно один раз, на первые 12 месяцев; сверх них — $0.07 за конверсию; органика бесплатна [факт: appsflyer.com/pricing]. Конверсия — платная (неорганическая) установка или повторное вовлечение, которые AppsFlyer атрибутировал.

## 5. Модель данных и витрины

**`dim_player`:**

- дата установки, первые платформа / страна / билд;
- канал установки: `ua_source`, `ua_campaign_id`, `ua_adset_id`, `ua_ad_id`, `ua_site_id`, `attribution_quality`;
- флаг «платящий игрок», дата / SKU / оффер / placement первой покупки;
- LTV на сегодня (IAP net, реклама);
- сегмент по платежам, группы A/B, флаг оттока.

**`fct_player_day`** (одна строка на игрока и день): сессии, время в игре, прогресс, источники и траты валют, IAP gross/net, возвраты, выручка с рекламы и показы по форматам.

**Витрины:**

| Витрина | Отвечает на |
|---|---|
| `monetization_daily` | ARPDAU (IAP / реклама), доля платящих, ARPPU, доля возвратов — по платформе и стране |
| `ltv_curves` | LTV за дни D0..D180 по когорте × платформа × страна; канал добавляем только для Android, iOS с ATT и Apple Ads на iOS (§3.2). Есть флаги зрелости: если когорта ещё не прожила N дней, значение LTV на день N помечено как неокончательное. Это вход для прогноза LTV и будущего ROAS |
| `first_purchase_path` | Путь игрока до первой покупки: когда (интервалы времени от установки), на каком уровне, через какие потоки офферов (`flow_id`), с каким оффером, placement, `trigger` и `src` |
| `offer_funnel` | Одна строка на поток IAP (`flow_id`): показ оффера → начало покупки → оплата → выдача; последний достигнутый шаг, шаг ухода (закрытие по `action`, ошибка по `reason`), время между шагами. Срезы: offer_id × placement × `trigger` × `src` × сегмент (платящий или нет, когорта, канал, `lvl`) |
| `ad_funnel` | Одна строка на поток рекламы (`flow_id`). Rewarded: возможность показа → реклама загружена (`ready`) → предложение → согласие → показ → досмотр → награда; предложение, согласие, досмотр и награда есть только у rewarded. Interstitial: возможность → загружена → показ → ошибка или выручка → закрытие. Баннер: место на экране → место ушло с экрана, с числом показов и выручкой за поток. Плюс выручка на возможность показа. Срезы: формат × placement × `trigger` × `src` × сегмент |
| `rewarded_funnel` | Влияние rewarded на удержание и прогресс: потоки rewarded из `ad_funnel` в сравнении с поведением игрока до и после |
| `ad_fatigue` | Показы на DAU в сравнении с удержанием и сессиями, по сегментам |
| `ads_vs_iap` | Выручка с рекламы у платящих; не снижает ли реклама покупки и наоборот; поведение после первой покупки |
| `economy_by_segment` | Источники и траты валют: платящие против неплатящих |
| `ab_monetization` | ARPU, конверсия, рекламная выручка по вариантам: SRM-проверка (нет ли перекоса в размерах групп), доверительные интервалы. Группа игрока — его первое назначение: Firebase назначает группу по установке, и после переустановки или на втором устройстве игрок может попасть в другую. Серверная выручка относится к группе игрока. Игроки с больше чем одной группой в одном эксперименте считаются отдельно и в результат не входят; их доля — в `dq` |

Контекст игрока в воронках (кто он) берётся на момент потока из `dim_player`, `fct_player_day` и последнего `session_snapshot` до начала потока. Деньги на поток: IAP — по `iap_purchase.transaction_id` (вместе с `flow_id`) из `fct_iap`; `iap_granted` только отмечает выдачу, поэтому «оплачено, но не выдано» остаётся в своём потоке. Реклама — по `show_id`, у баннеров — сумма клиента `ad_close.revenue` (§4.2).

**Слабое место:** связь потока с деньгами держится на клиентских событиях, а их доставка не гарантирована (streaming-выгрузка GA4 работает по принципу best-effort [факт: support.google.com/analytics/answer/9358801]). Итоговые суммы от этого не зависят: они приходят от сервера и сторов [вывод]. Размер потерь измеряем в `dq`: доля строк `fct_iap` без потока и доля строк `ad_impressions` без потока по всем форматам. У баннеров проверка сравнивает суммы клиента в `ad_close` с User-Level по игроку × день UTC × ad unit × placement; поток относится ко дню UTC своего `ad_close`, игроко-дни с потоком баннера через полночь UTC в сравнение не входят, их доля показана в `dq`.

## 6. Подводные камни монетизации и атрибуции

| # | Камень | Решение |
|---|---|---|
| 1 | ID игрока задан после инициализации SDK | Фиксированный порядок (§2) + `dq` на долю без ID |
| 2 | `player_id` сбрасывается при переустановке | Аккаунт Nakama с входом через Game Center / Play Games; доля анонимных — в `dim_player.account_type` |
| 3 | Тестовые и песочные покупки | `environment` в таблице Nakama; тестовые покупки Google Play определяются по списку лицензионных тестеров. Такие покупки исключаются |
| 4 | НДС и комиссии (Google в 2026 году по рынкам) | Android — net каждой покупки из Orders API; iOS — выплата за единицу из отчёта продаж App Store Connect (ставка Apple для подписок после года видна по Proceeds Reason); `net_source` показывает источник, доли `ambiguous` и `missing` — в `dq` (§4.1) |
| 5 | Возвраты приходят неделями позже | LTV когорт пересчитывается; в витринах помечено «net на дату» |
| 6 | Курсы валют | `fx_daily` на дату платежа |
| 7 | Окно MAX API 45 дней | Алерт на свежесть; повторная загрузка последних 3 дней |
| 8 | Выручка MAX частично оценочная | Источник — MAX как есть, без подгонки под выплаты сетей. Сверка полноты загрузки с Revenue Reporting; в `dq` доля выручки по `precision` по сетям (rewarded и interstitial); у баннеров — доля `revenue_exact / revenue` из `ad_close` (§4.2) |
| 9 | iOS без ATT = «органика» в GCD | `attribution_quality`; на iOS без ATT канал = «неизвестно», кроме Apple Ads |
| 10 | Цифры DWH и AppsFlyer не совпадают | Правило одного источника + еженедельная сверка |
| 11 | Сети не видят рекламную выручку (нет ROI360) | Событие с `af_revenue` из колбэка MAX (§4.3) |
| 12 | Часовые пояса: у Apple отчёты по тихоокеанскому времени (Pacific Time) [факт], у MAX User-Level — UTC [вывод] | Сверка со сторами помесячно или с допуском на границы дней |

## 7. Что настроить и проверить у себя

1. **MAX:** Report Key (ключ доступа к отчётам) для User-Level Ad Revenue API и Revenue Reporting API; проверить в аккаунте MAX цену и условия доступа User-Level API.
2. **AppsFlyer:** тариф Growth; спросить AppsFlyer до запуска, платны ли in-app события; Aggregate Pull API платный, покупаем его только если ручной сверки по дашборду не хватит; настроить SKAN Conversion Studio и проверить на тестовой сборке, обновляет ли SDK conversion values ([tracking-plan.md §7](tracking-plan.md), п. 6).
3. **Meta:** принять условия AMM в AppsFlyer и включить Meta Install Referrer (без этого Meta на Android частично будет «органикой»).
4. **App Store Connect:** shared secret (ключ для проверки чеков) в Nakama; URL Nakama для ASSN V2; ключ In-App Purchase API для App Store Server API (задание Get Transaction Info); ключ App Store Connect API для отчётов `salesReports` и `financeReports`; включить Game Center; вступить в Small Business Program (15%), если выручка до $1M.
5. **Play Console:** бакет GCS (Google Cloud Storage) для отчётов; сервисный аккаунт для Developer API (тот же получает Nakama); RTDN через Pub/Sub на адрес Nakama; Play Games Services для входа.
6. **Nakama:** ключи Apple и Google в конфиге IAP; `notifications_endpoint_id` для уведомлений; Game Center и Google в настройках входа.
