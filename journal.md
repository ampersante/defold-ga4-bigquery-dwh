## 2026-10-24

**Актуальность фактов.** Факты в `docs/` (документация Google, Apple, AppsFlyer, AppLovin, код расширений Defold и Nakama) собраны и проверены на эту дату.

**Решения владельца:**
- Медиация — AppLovin MAX. Трафик закупается в любых рекламных сетях.
- Паблишера нет, все аккаунты свои. Будет ли паблишер, неизвестно.
- MMP — AppsFlyer Growth, без ROI360 и Data Locker (оба платные).
- DWH не дублирует MMP. Атрибуция попадает в DWH только как атрибут игрока.
- ROAS, CPI и затраты в DWH сейчас не считаем. Модель должна позволять добавить их позже без переделок.
- EU consent вне рамок.
- Бэкенд — Nakama, потому что нужно живое PvP. Firebase (нет живого PvP и SDK для Defold) и RevenueCat (1% выручки) рассмотрены и отброшены. Владелец предпочитает свой код на официальных библиотеках платным сервисам.
- Сопровождает бэкенд владелец с помощью агента.
- Вход: Game Center (iOS) и Google Play Games (Android) без кнопок, анонимный аккаунт как запасной. Сторонние соцсети не используем: они оправданы на зрелых играх.
- Покупка выдаётся только после проверки на сервере. Подписки поддерживаются.
- 20 аналитических вопросов владельца:
  - поведение по каналам — в DWH как атрибут игрока;
  - состав CPI (вопрос 5) — в консолях сетей;
  - CPI (вопрос 3) — позже;
  - реестр гипотез (вопрос 20) — вне рамок, позже, возможно, через ИИ и MCP к BigQuery.

**Находки:**
- В исходниках Nakama: чеки StoreKit 1 проверяются через устаревший `verifyReceipt`; цена и валюта покупки не хранятся.
- В `britzl/extension-gamekit` есть только устаревший `playerID`. Подписи Game Center для проверки на сервере нет.

**Работа с документами:** созданы `architecture.md`, `monetization-attribution.md`, `tracking-plan.md`. Три документа вычитаны на простоту языка с механической сверкой: числа, ссылки и идентификаторы сохранены.

## 2026-11-03

**Кросс-ревью документов** другими моделями: Codex (gpt-6.1-sol, xhigh) и Grok (glm-5.3, max), роль work-evaluator. Оба вердикта — UNSOUND. Каждая находка перепроверена по первоисточникам (код Nakama, документация Google, Firebase, Dataform, Apple, AppsFlyer, MAX). Подтверждены 18, отклонённых нет. Владелец решил внести все; исправления внесены в `docs/`.

**Находки, которые меняют устройство:**
- Nakama хранит на Android в `transaction_id` `purchaseToken`, а `orderId` — только в `raw_response`. Ключ склейки на Android — `orderId`: `purchaseToken` длиннее лимита параметра Firebase.
- У подписок в Nakama одна строка, которая перезаписывается при продлении. Нужен свой журнал уведомлений `nakama_subscription_events`.
- Сумма покупки — из стора (Google Orders API; на iOS — подписанная транзакция в хуке Nakama), клиентское событие — запасной источник; `fct_iap.amount_source`.
- `seq` даёт нижнюю оценку потерь: хвост событий у не вернувшихся игроков не виден.
- Assertions Dataform не останавливают витрины без явных зависимостей.
- Группы A/B Firebase назначаются по установке; у игрока может быть несколько групп.
- У игрока может быть несколько установок: `dim_install`, когорта и канал — по первой установке.
- Выгрузка шаблона Remote Config не содержит значений вариантов A/B — они хранятся в `ref_tests`.
- Nakama не запрашивает пропущенные уведомления сторов и на часть ошибок записи отвечает 200: задание по Voided Purchases постоянное, после восстановления бэкапа — повторный запрос событий.
- В ответе Google по подписке v2 списанной суммы нет (поля цены — только в старом v1, Nakama его не вызывает). Хук хранит `latestSuccessfulOrderId` продления, сумма — из Orders API.
- AppsFlyer на iOS запускается по ответу на ATT или по таймеру от холодного старта, со статусом `not_determined`: иначе ушедшие в первой сессии остаются без атрибуции.

**Повторные проверки:** Grok — SOUND & VERIFIED (PvP отложен владельцу). Codex — три ограниченных повтора, открытые замечания 13 → 4 → 1 → 0, итог SOUND & VERIFIED.

**Открыто:**

## 2026-11-04

**Решения владельца:**
- Основной путь событий — Firebase / GA4. Свой сборщик (очередь на клиенте → пакетный RPC Nakama → BigQuery Storage Write API) — запасной вариант, строим, только если измеренные потери высоки. Хостинг — Vultr или netcup.
- Выручку рекламы не калибруем по выплатам сетей и не подключаем API отчётов сетей. Источник — выручка MAX.
- PvP — второстепенный цикл: минимальные клиентские события матча. Если станет основным, результат и рейтинг — из обработчика матча Nakama. Пункт 4 закрыт.
- Монетизация — сквозные воронки: у каждой возможности (офер, рекламная точка) свой `flow_id` от точки входа до исхода и денег.
- Разметка и настройка должны работать правильно с запуска: ни одна проверка не ждёт платного трафика или реальных продаж. Открытые факты закрываются документацией, тестовым билдом или песочницей до запуска либо устройством, верным при любом ответе. Список проверок §7 tracking-plan сокращён с 9 до 5: часовой пояс отчёта Apple (Pacific Time) и количество в покупке (всегда 1 в extension-iap) подтверждены, Customer Price убран из подбора строки, отбор по офферу переписан так, чтобы при несовпадении строк результат был `ambiguous`, а не неверный net. Остальные 12 пометок закрыты исследованием: автоматический `in_app_purchase` будет на обеих платформах (DWH его не использует); AppsFlyer SDK 7 не ждёт ATT, поэтому таймер `start_sdk` обязателен; SKAN Conversion Studio выставляет значения сам; 12k конверсий Growth — разово на первый год; история уведомлений Apple — 180 дней, после восстановления из бэкапа запрашивается без `onlyFailures`; ECB (29 валют) не покрывает валюты Apple — нужен источник шире, валюта без курса даёт пустую сумму в USD и оповещение. Без официального ответа остались: цена in-app событий AppsFlyer, цена MAX Reporting API, срок хранения очереди Firebase на устройстве — на корректность данных не влияют.

**Находки, которые меняют устройство:**
- Расширение Defold IAP на iOS работает на StoreKit 1 и отдаёт только чек приложения, поэтому Nakama проверяет покупки через устаревший `verifyReceipt`; цены в ответе нет. Хук уведомлений Apple для разовых покупок срабатывает только на возврат. Цена iOS — ежедневным заданием App Store Server API Get Transaction Info по `transactionId` → `apple_transactions`.
- `verifyReceipt` устарел с 2023 года, но работает (проверка запросом 2026-11-03), дата отключения не объявлена. Запасной путь проверки — тот же Get Transaction Info.
- Net на iOS — поштучно из отчёта Sales («Developer Proceeds (per unit)»), а не коэффициентом. Строка отчёта выбирается по Proceeds Reason (из оплаченного срока подписки) и Order Type (из оффера в JWS); если остаются строки с разной выплатой, net не назначается (`ambiguous`). Расхождение с финансовым отчётом — не только курс: Apple называет ещё сроки закрытия периода и неполученные платежи.
- Apple Ads атрибутируется AppsFlyer без ATT — подтверждено по статье AppsFlyer.
- Nakama `/v2/event` не годится как сборщик: одно событие за вызов, очередь в памяти при переполнении выбрасывает события после ответа клиенту «успех».
- Дневная выгрузка GA4 полная и дописывается 2 дня; best-effort — только потоковая. Принудительной отправки событий в Firebase SDK нет.
- `revenuePrecision` MAX показывает, где выручка показа точная (`exact`), а где оценка; Meta и при ставках отдаёт оценку.

**Ревью плана:** plan-reviewer — REJECT (11 замечаний, одно — неверная посылка «ставки ⇒ точная выручка»), после исправлений — APPROVE_WITH_CHANGES, замечания внесены.

**Кросс-ревью правок документов:** Codex (gpt-6.1-sol xhigh) — UNSOUND, 7 замечаний; Grok (glm-5.3 max) — UNSOUND, 6 замечаний. Всё внесено. Повторная проверка: Grok — SOUND & VERIFIED; Codex — 6 из 7 закрыты, две регрессии (промо-офферы ищутся в колонке Order Type, а не Promo Code; баннерным суммам нужны `ad_unit` и разрез по суткам UTC) — внесены. Итог: Codex и Grok — SOUND & VERIFIED.
